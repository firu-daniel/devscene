# Cross-layer conventions

> **Read this when:** you are implementing, reviewing or planning **any** change — these are the rules that hold in every layer, and they are also the `general` layer's own rules. **Skip when:** never; `.claude/context/cli.md`, `.claude/context/plugin.md`, `.claude/context/docs-retrieval.md`, `.claude/context/graphscene.md` and `.claude/context/devscene-flow-host.md` all assume this one has been read.

**Purpose.** The rules a change must satisfy whichever layer it lands in, and the vocabulary the harness uses to talk about this project.

## The stack, in the words the rules below use

- **`cli/` is TypeScript** targeting ES2022 under `module`/`moduleResolution: NodeNext`, compiled by `tsc` to `cli/dist/`, run on Node `>=20.11.0`. `strict`, `noUncheckedIndexedAccess`, `noUnusedLocals` and `noUnusedParameters` are all on, so an unused binding and an unchecked index access are build failures rather than review findings. (`cli/tsconfig.json`, `cli/package.json`)
- **The published package declares no required runtime dependency.** `cli/package.json` carries `devDependencies` and no `dependencies` key, and every static value import in `cli/src` resolves to a `node:` builtin or to a relative sibling; an erased `import type` from an optional retrieval peer is permitted (`cli/src/retrieval/store.ts`, `cli/src/retrieval/server.ts`, `cli/src/retrieval/models.ts`). Adding a required runtime dependency is a decision raised as a `stale-rule` entry for a supervised `/analyze` re-run or a hand edit, never a change an implementing run makes: a hand-rolled flag parser and a hand-written configuration check exist because of it (`cli/src/cli.ts` → `GLOBAL_OPTIONS`; `cli/src/config/check.ts` → *"This is not a schema validator, and it must never grow into one"*).
- **One carve-out: docs retrieval.** The libraries docs-catalog retrieval needs — the embedded Postgres with its vector and BM25 extensions, the local embedding runtime and the MCP server SDK — are declared as **optional** peer dependencies (`peerDependenciesMeta`), never under `dependencies`, and repeated under `devDependencies` so this workspace's own `npm ci` installs them for building and testing. Only a dynamic `import()` on the retrieval path loads them, so a verb that does not retrieve loads nothing new; they are installed only for an adopter who turns retrieval on; and a missing one fails with an error that names it and says how to install it. The carve-out covers retrieval and nothing else: any other package still goes through the rule above.
- **`plugin/` is prose and shell**: Markdown **agent and command** contracts carry YAML frontmatter and are the only assets that may — an **instruction** document opens on its own H1 with no frontmatter fence, and adding one to an instruction file is a defect (`plugin/instructions/unit_loop_core.md` → the opening `# The unit loop` heading; `plugin/instructions/mode_contract.md` → the opening `# Mode contract` heading) — plus `bash` guard hooks. The `bash` floor is **3.2**, so macOS's `/bin/bash` qualifies, and a guard's prerequisites are `git` and `jq` 1.5 or newer, with one exception: `plugin/hooks/git-trust-file-guard.sh` runs `readlink` (without `-f`) when a file-tool target is itself a symbolic link, and a missing or failing `readlink` on that branch is a refusal (`plugin/hooks/README.md` → `## Prerequisites`).
- **The Python layers — `docs-retrieval-service/`, `graphscene/` and `devscene-flow-host/` — are Python `>=3.11`**, each a `hatchling`-built `src/` layout with its own `pyproject.toml` and `uv.lock`; linted by `ruff` (`target-version = "py311"`, `line-length = 100`, rule sets `E`, `F`, `I`, `B`, `UP`), typechecked by `mypy` `strict` over `src` and `tests`, tested by `pytest` with `-p no:cacheprovider -rs` (`docs-retrieval-service/pyproject.toml`, `graphscene/pyproject.toml`, `devscene-flow-host/pyproject.toml` → `[tool.ruff]`, `[tool.mypy]`, `[tool.pytest.ini_options]`). Each layer's own document carries what is particular to it.
- **Every Python command goes through `scripts/python-service.sh`, run from the repository root**, a non-default package selected with a leading `--package <dir>`; nothing invokes `uv`, `ruff`, `mypy` or `pytest` directly (`docs-retrieval-service/README.md` → `## Standing it up`; `graphscene/README.md` → `## Running the toolchain`; `devscene-flow-host/README.md` → `## Running the toolchain`). Every gate leg runs through `uv run --frozen --no-sync`, so no leg reaches the network or changes the environment; `bash scripts/python-service.sh provision`, run outside any sandbox, is the one route that syncs every package (`docs/development.md` → `## 5. Verifying a change`, **Gate 13**).
- **`schemas/` is JSON Schema**, validated by `ajv` from the workspace root (`package.json` → `validate:config`).

| `general` | `.` | Everything else at the root: `schemas/`, `docs/`, `examples/`, `evals/`, the root prose documents and the workspace manifest | this document |

- **`general` is the catch-all and must stay one.** `layers` is required to contain an entry whose `path` is `.`; a configuration without one is rejected, which `schemas/negative/layers-no-catch-all.json` exists to prove. A change whose files sit under another layer's path belongs to that layer and never to `general`.
- **Neither shipped half may reach into the other at run time.** `cli/src` names `plugin/` files only inside doc comments and in `doctor`'s own report text, and `plugin/` names `cli/src` files only in prose citations; no module imports across the boundary and no shell asset sources one. Making either one execute the other is a new coupling raised as a `stale-rule` entry for a supervised `/analyze` re-run or a hand edit, never a change an implementing run makes. (`cli/src/doctor/checks.ts`, `plugin/hooks/README.md`)
- **The two halves are coupled by contract, not by import**, in one direction: `cli/` writes what an adopting repository gets, `plugin/` reads what is there. So a change to the shape of `devscene.config.json`, `stateDir` or `scriptsDir` starts in `cli/` and `schemas/`; the plugin contracts that consume it are downstream of it, and a plugin contract reading a shape the schema does not carry is a defect.
- **`cli/` reaches the Python backend only as a process, by names `cli/src/retrieval/pythonBackend.ts` owns.** The console script, its sub-commands, the database variable, the default connection string, the launcher's unavailable-backend exit and the `self-check` line contract are spelled there once; every copy outside the compiler is a mirror that module's `MIRRORS.` header declares, and an undeclared mirror is a defect (`cli/src/retrieval/pythonBackend.ts` → *"The rule this module exists to enforce"*).
- **The two docs-retrieval backends are one wire with two implementations.** The server name `devscene-docs`, the tool `search_docs` and the permission string `mcp__devscene-docs__search_docs` are the TypeScript side's, and the Python side reproduces them (`docs-retrieval-service/src/devscene_docs_retrieval/wire.py` → `SEARCH_TOOL_NAME`); a difference a client can observe is legal only where `docs-retrieval-service/README.md` → **Deliberate wire differences.** names it. Parity is asserted by the Python suite against the compiled TypeScript under `cli/dist`, never against a copy (`docs-retrieval-service/tests/ts_bridge.py` header), so a change to `cli/src/retrieval/` is graded by gate 13c as well as gate 4.
- **A model-pin bump is a deliberate edit to the pin constants together with `MODEL_VERSION`, on both retrieval paths where both move** — `cli/src/retrieval/models.ts` and `docs-retrieval-service/src/devscene_docs_retrieval/models.py` (`EMBEDDING_REVISION`, `RERANK_REVISION`, `MODEL_VERSION`) — and the pin table in `docs/retrieval.md` → **Models.** moves with them (`docs/development.md` → **Model pins and the drift notice.**).
- **`graphscene/` depends on no harness code, and the dependency points one way.** Harness-side code that drives GraphScene — reading the harness's configuration, executing its agents, its planning hooks — goes in its own `devscene`-prefixed distribution outside `graphscene/`, which depends on `graphscene`; nothing under `graphscene/` names it (`graphscene/README.md` → `## The boundary`; enforced by `graphscene/tests/test_boundary.py`). The library's own boundary is `.claude/context/graphscene.md` → `## What it may depend on`.
- **`devscene-flow-host/` is the harness side of that boundary — the harness's GraphScene host.** It holds only the code that feeds GraphScene the harness's configuration, records, predicates, executor configuration and hooks, and the commands over it; any other DevScene Python integration gets its own `devscene`-prefixed package rather than a place there, and anything useful without DevScene goes in `graphscene/` instead (`devscene-flow-host/README.md` → `## What it is`; `devscene-flow-host/src/devscene_flow_host/__init__.py` module docstring). It reaches `graphscene` through its public surface only — `import graphscene` or `from graphscene import <name in graphscene.__all__>`, never a submodule such as `graphscene.engine` — and GraphScene never imports it (enforced from this side by `devscene-flow-host/tests/test_boundary.py`, from the other by `graphscene/tests/test_boundary.py`). **Adopters never import it** (`devscene-flow-host/README.md` → `## What it is`); the route by which it reaches an adopter is not built yet (`## Not determined`).
- **`devscene-flow-host`'s lock follows GraphScene's**; how it sources `graphscene` is `devscene-flow-host/README.md` → `## What it may depend on`. A change to `graphscene/pyproject.toml` → `[project] dependencies` re-locks `devscene-flow-host` with `bash scripts/python-service.sh --package devscene-flow-host lock`; `devscene-flow-host/tests/test_graphscene_dependency.py` (gate 13j) fails until it is done (`devscene-flow-host/pyproject.toml` → `[tool.uv.sources]`; `devscene-flow-host/README.md` → `## The lock follows GraphScene`).

### Where a new responsibility goes

Settle which audience it serves before choosing a file.

| The new thing is… | It goes in |
|---|---|
| behaviour of this CLI itself | a module under `cli/src/<area>/` |
| a file a future adopter receives | `cli/templates/`, mirroring the path it lands on in the adopting repository |
| a shape `devscene.config.json` may take | `schemas/devscene.config.schema.json` first, then its readers |
| a contract an agent or a flow reads | `plugin/agents/`, `plugin/commands/` or `plugin/instructions/` |
| behaviour of the Python docs-retrieval backend | a module under `docs-retrieval-service/src/devscene_docs_retrieval/` |
| generic flow-graph navigation | `graphscene/src/graphscene/` |
| code that feeds GraphScene the harness's configuration, records, predicates, executor configuration or hooks, or a command over it | `devscene-flow-host/src/devscene_flow_host/` (`devscene-flow-host/README.md` → `## What it is`) |
| any other harness-side Python integration | its own `devscene`-prefixed package outside `graphscene/` and `devscene-flow-host/` (`devscene-flow-host/README.md` → `## What it is`; `graphscene/README.md` → `## The boundary`) |
| a measured fact or a decision of record | `docs/`, and nowhere else |

**A responsibility that already has a home does not get a second one.** Each of these is a stated monopoly, and the code must keep it true:

- `cli/src/cli.ts` is the only place a thrown value becomes an exit code, and nothing in the package calls `process.exit()` (`cli/src/core/errors.ts` → the module header's rule 1).
- `cli/src/core/git.ts` is the only module that invokes `git` for repository state or for a path, with one bounded exception that its own header names — `cli/src/generators/githooks.ts`, which reads and writes the `core.hooksPath` **setting**. A further `git` invocation anywhere in the package belongs in `cli/src/core/git.ts`.
- `cli/src/core/writer.ts` is the only module that writes into an adopting repository, with two exceptions its header names: the derived docs-retrieval index under `<stateDir>/docs_index/`, written only through `cli/src/retrieval/store.ts` (`openPgliteStore`), and the `search_docs` query log at the operator's `RETRIEVAL_LOG_ENV` path, which may land inside or outside the repository and is written only by `cli/src/retrieval/queryLog.ts`. Every mutating filesystem call in `writer.ts` is inside its commit boundary, `commitWrite`, except `probeWritable`, `doctor`'s writability probe, which is part of no plan. A generator enqueues a `WriteRequest` and picks a policy from that module's table; it never calls `fs` itself and never invents a policy.
- `cli/src/machine/registry.ts` is the only module that resolves, reads or writes the machine-local registry of initialized repositories — its path, its JSON shape and its staleness grading (`cli/src/machine/registry.ts` → the module header's rule).
- `cli/src/retrieval/pythonBackend.ts` is the only TypeScript module that spells a name the Python backend is reached by (its header's rule, above).
- `plugin/hooks/lib/harness-config-lib.sh` is the only place **any** shell asset in `plugin/` resolves the repository it is judging, loads that repository's `devscene.config.json`, answers whether a branch is protected, or builds its safe-prefix set (`hc_safe_prefixes`). Its reach is wider than the guards — `plugin/scripts/reserve-qa-user.sh` and `plugin/scripts/release-qa-user.sh` source it too, and neither is a guard — so a new non-guard script needing any of those answers sources this library rather than re-deriving them (`plugin/hooks/lib/harness-config-lib.sh` → the header's *“the one place every guard hook and the two QA-user helpers”* and its `WHO SOURCES THIS, AND HOW` paragraph).

**Before adding a copy of anything, grep for it.** `cli/src/core/repoPaths.ts` exists because several modules had each carried a private copy of one normalisation, the copies had drifted, and two divergent bodies had been given the same name — so a caller moved between those two files silently changed behaviour, with no compile error and no test. Its header is the worked cost of getting this wrong.

### The order files are created, so a half-built feature is still coherent

Contract before consumer, always. The shapes this tree has:

1. **A configuration key** — `schemas/devscene.config.schema.json`, then `cli/src/config/model.ts`, then `cli/src/config/check.ts`, then `docs/config.md` §5. **These four are one contract in four places**, and both source modules say so in their own headers: a key in the model that is not in the schema is a key no configuration may legally carry, and a key in the schema that is not in the check is reported as unknown — a false error.
2. **A CLI subcommand** — the module under `cli/src/commands/` exporting its own `Subcommand`, then its row in `SUBCOMMANDS` (`cli/src/commands/registry.ts`). That table is the single source for usage text, per-command `--help` and dispatch, so nothing else has to change and nothing else may be edited to make the command appear.
3. **A plugin contract** — the asset itself with valid frontmatter, then the instruction or command that dispatches it, then every file that cites it. A contract that nothing dispatches and a dispatch of a contract that does not exist are both defects; `plugin/agents/README.txt` gives the regeneration commands for the sample-pointer case under `Sample fixture pointers`.

**The plugin corpus quotes its own literal wire strings across files, so a rename is an edit to every quoting file.** Before changing a field name, a dispatch key or a quoted literal in `plugin/`, `grep -rn` the exact string across `plugin/` and take the whole result set with you. A literal only one side knows about is a silent contract break (`## Commit-message policy` → **Changing any fixed subject is a multi-file edit.** below).

## Configuration is the source of truth, and it is read at run time

**`devscene.config.json`, at the adopting repository's root, is the source of truth for everything that varies between adopters** — the layers, the verification commands, the branch policy, the artifact and script directories, the phase toggles. Nothing caches it and nothing mirrors it: each consumer re-reads the file on each run, from the root it resolved for itself.

- **No configured value is ever frozen into a generated file.** An outer-loop script is copied byte for byte rather than rendered precisely because it reads the configuration at run time; a guard whose protected-branch set was baked in at generation time enforces the wrong set the moment that list changes, and does it silently (`docs/cli.md` → *"Two families land in `scriptsDir`"*).
- **No branch name, no directory name and no command name from any one adopter appears as a literal in `plugin/`.** The corpus writes `<state_dir>`, `<scripts_dir>`, `<default_branch>` and their siblings; a guard reads the real values through the shared library (`plugin/hooks/README.md` → *"No branch name is baked into any of these files"*). The configuration schema's own default is not an adopter's value, so `plugin/hooks/lib/harness-config-lib.sh` (`hc_protected_patterns`) may fall back to `main`, the `protectedBranches` default in `schemas/devscene.config.schema.json` and `cli/src/config/model.ts`.
- **Every path in `devscene.config.json` is repo-relative**, and the root it resolves against comes from a **bare** `git rev-parse --show-toplevel` — never a hardcoded absolute path, never a substitution nested inside another command, never a value stashed across tool calls. A bare invocation is what an unattended run's permission profile can allow-list; the same probe wrapped in a compound statement is a different string, which an unattended run refuses (`docs/config.md` → `## 1. The three resolution classes`; `cli/src/core/git.ts` → the header's invariant 2).
- **Which normalisation a repo-relative path takes is part of the contract, and the two are deliberately spelled differently**: `normalizeRepoDir` leaves a `..` where it found it and is the default; `normalizeRepoPathStrict` resolves it and is for a caller that keys on the result (`cli/src/core/repoPaths.ts`).
- **The Python docs-retrieval backend reads `devscene.config.json` read-only, for `docs.root` and `layers[]` only**, from the repository its `--repo` names (`docs-retrieval-service/README.md` → `## Standing it up`; `docs-retrieval-service/src/devscene_docs_retrieval/service.py`). `graphscene/` never reads it (`graphscene/README.md` → `## The boundary`).

**Serialized names and in-language names are the same identifiers.** Every key of `devscene.config.json` is `lowerCamelCase`, and the property of the interface that reads it carries that key verbatim — `projectName`, `defaultBranch`, `protectedBranches`, `stateDir`, `appDir`, `scriptsDir`, `githooksDir`, `agentModel`, `pushEnvPath`, and `name` / `path` / `conventions` inside a `layers` entry. There is no mapping layer and none may be introduced: the schema's `properties` and `cli/src/config/model.ts`'s interfaces are read against each other key for key.

**The shared constants have owners, and a value is imported from its owner rather than retyped**: `CONFIG_FILENAME` and `CONFIG_VERSION` in `cli/src/config/model.ts`; `EXIT` in `cli/src/core/errors.ts`; the action markers, labels and order in `cli/src/core/report.ts`; the Python backend's names in `cli/src/retrieval/pythonBackend.ts`; the safe-prefix set in `plugin/hooks/lib/harness-config-lib.sh`; the deny-by-basename set in `plugin/hooks/autonomous-script-allowlist-guard.sh`. Where a total mapping over a union is involved, type it as a total record so adding a member is a compile error until every table is extended (`cli/src/core/report.ts` → `Reporter.counts`).

- **A persisted key has the same rule, and the machine-registry keys are owned by `cli/src/machine/registry.ts`** — `REGISTRY_FILENAME`, `REGISTRY_SCHEMA` and `REGISTRY_FILE_MODE`. That module's header declares the single mirror outside the package, `MACHINE_REGISTRY_FILENAME` in `cli/templates/scripts/autonomous-watcher.sh`, which is a template an adopter receives rather than an import site; a mirror the header does not declare is a defect, and a new persisted artifact joins the module that owns it rather than being named at its use site.
- **An environment-variable name is a constant with an owner too**: `CLAUDE_HOME_VARIABLE` (`cli/src/machine/paths.ts`) and `SELF_ADOPT_ENV` (`cli/src/commands/init.ts`), each read through its constant and never retyped as a literal — including in the message that names it to a reader. The Python layer's form of this rule is `.claude/context/docs-retrieval.md` → `## Constants, keys and environment variables`.

## Shared code, and where it lives

- The CLI's shared modules are `cli/src/core/` — errors, output, the write engine, git, JSON, path resolution, path normalisation, templating, prompting. A value or behaviour two `cli/src` areas need lives there, never duplicated into both.
- The shared shell library is `plugin/hooks/lib/harness-config-lib.sh` — the guards' and the QA-user helpers' alike — sourced by a path computed from `${BASH_SOURCE[0]}` and never by the plugin-root token, which the runtime does not export into a script's environment.
- The flows' shared prose is `plugin/instructions/*_core.md`: a mode-free core carries the flow, and a **thin fork** overrides only what the mode changes. A rule is stated once and a mode difference is visible as a fork, never as a second copy that drifts (`plugin/instructions/README.md`).
- The Python layers share a toolchain runner, `scripts/python-service.sh`; each package is its own distribution with its own lock. `devscene-flow-host` reaches `graphscene` through its public surface only (`## The layers` above), and `graphscene/` imports nothing of the harness (`graphscene/README.md` → `## The boundary`).

## Registries and dispatch tables

There is no navigation surface in this project; its analogue is the set of tables that route a name to an implementation, and each is a single source with no second list beside it.

- `cli/src/commands/registry.ts` → `SUBCOMMANDS` routes a CLI verb to its module and renders usage from the same array.
- `cli/src/cli.ts` → `GLOBAL_OPTIONS` is the single source for both the argv parser and the `Options:` block.
- `plugin/hooks/hooks.json` registers every guard, and the event names go one level down inside a `{"hooks": { … }}` wrapper (`docs/development.md` → `## 3. Manifest facts a contributor must not rediscover`).
- `devscene.config.json` → `layers` routes a changed path to the layer that owns it and to that layer's rules document.
- `cli/src/detect/signals.ts` is an ordered first-match-wins table, so a row added to it can shadow a later row or be shadowed by an earlier one.
- `scripts/python-service.sh`'s package table is what gate 13 and `provision` iterate: gate 13 holds each package in it to the same bar (`docs/development.md` → `## 5. Verifying a change`, **Gate 13**).

## Output, logging and errors

**The CLI has one output surface: `Reporter` (`cli/src/core/report.ts`).** Every command writes through it and calls `console` never. Only two files under `cli/src` may call the global `console` object: the entry point `cli/src/cli.ts`, which prints `--version`, the usage block, the unknown-command refusal and the final error line directly, because those are argv-level answers that precede or follow any reporter; and `cli/src/core/report.ts` itself, whose constructor installs `console.log` / `console.error` as the reporter's own default sinks, which is why injecting a sink is what redirects output rather than stubbing `console` (`cli/src/core/report.ts` → the `Reporter` constructor's `options.out ?? …` / `options.err ?? …`). Three properties depend on the rule: `--quiet` behaves the same everywhere, the write engine's action log and the human-readable log are one log, and the output is **plain ASCII — no colour escapes, no emoji** — so a test can diff it verbatim.

- `info` / `step` / `ok` / action lines / `summary()` are narration on stdout, suppressed by `--quiet`. `warn` and `fail` go to stderr and always print. `result()` is the one line a caller came for and prints on stdout whatever the flags are.
- Injecting a sink (`ReporterOptions.out` / `err`) is how a test captures output. Do not stub `console`.

**Errors carry their own exit code and are never turned into one locally.** Throw `HarnessError` for anything the CLI anticipated — a refusal, a failed check, bad usage — which exits `EXIT.FAILURE`. Use `internal(message)` for a fault in this CLI or in the assets it ships, which exits `EXIT.INTERNAL` and appends the standard trailing sentence; do not hand-build `new HarnessError(…, EXIT.INTERNAL)`, and do not pass a message that already carries its own version of that sentence. Let every unanticipated throw propagate: `cli.ts` reports it as `(unexpected)`, and that code is the signal that the fault is a CLI bug rather than a misconfigured repository. **Every non-zero exit carries a message naming its cause** — a bare non-zero exit is indistinguishable from a crash to the run daemon. (`cli/src/core/errors.ts`)

**The Python backend follows the same shape in its own terms**: one anticipated-failure type, `ServiceError`, turned into an exit status only by `cli.main`, and anything else propagating with its traceback (`docs-retrieval-service/src/devscene_docs_retrieval/errors.py` → *"The rule this module exists to enforce"*). Its details are `.claude/context/docs-retrieval.md` → `## Errors and output`.

**A guard hook's output contract is narrower still.** It takes its payload on stdin and prints **at most one JSON object**. An allow-only guard emits `allow` or nothing, and for it failing closed means emitting nothing, which defers to the adopter's permission profile and costs a prompt — in an unattended run, a refusal — rather than a false permit. `plugin/hooks/git-commit-branch-guard.sh` may also answer `ask`. Only two guards in the plugin may answer `deny`, one per matcher: `plugin/hooks/autonomous-protected-branch-guard.sh` under `Bash`, which refuses only what it can prove, and `plugin/hooks/git-trust-file-guard.sh` under `Edit|Write|NotebookEdit`, which also refuses any payload it cannot read. (`plugin/hooks/README.md`)

## Shell assets

- **`#!/usr/bin/env bash`** on every shell file in this tree, and `*.sh` plus `githooks/*` are checked out with LF on every platform — a CR at the end of a shebang is read as part of the interpreter's name and fails with a message that never mentions a line ending (`.gitattributes`).
- **A guard hook uses `set -u` and never `set -e`** (`plugin/hooks/README.md` → `## Prerequisites`). A configuration it cannot resolve never produces a permit, and for an allow-only guard failing closed means never emitting `allow` (`plugin/hooks/README.md` → `## Fail closed — and what that means for an allow-only guard`).
- **A sourced library sets no shell options at all** — `plugin/hooks/lib/harness-config-lib.sh` and `cli/templates/scripts/lib/harness-run-lib.sh` both leave the sourcing script's shell exactly as they found it.
- **Never shell out to a recursive removal from `cli/src`.** A user-level `permissions.deny` on `rm -rf` is realistic, deny is evaluated before any allow and cannot be overridden, so a teardown implemented as a shelled-out `rm -rf` is silently blocked with no useful error. Use an in-process removal (`cli/src/cli.ts` header; `cli/src/core/writer.ts`, whose removals, `probeWritable`'s probe file and `replaceAtomically`'s abandoned temporary file, are each called on one file without `recursive`). A shipped script's own cleanup under `cli/templates/scripts` is outside this rule, because a permission rule is matched against the command an agent issues and not against what a script runs inside.
- **Never `git add -A` or `git add .`.** Staging is always an explicit repo-relative path set. A flow's commit point names a unit or an artifact kind and the commit wrapper derives the path set itself — the artifact table's paths, or the unit's changed paths with its findings folder kept apart — and stages exactly those (`cli/templates/scripts/commit-on-branch.sh` → THE STAGE SET; `cli/templates/scripts/lib/unit-commit-lib.sh` → `ucl_stage_set`); a plain-form call passes its explicit paths, which the wrapper stages and nothing else; the run watcher's and `remote-run.sh`'s artifact commits commit exactly one path, through `hr_commit_placed`, which builds the commit in a temporary index from the branch tip plus that one entry — leaving whatever the run has staged out of it — and runs no hook (`cli/templates/scripts/lib/harness-run-lib.sh`); `refresh-branch.sh` stages nothing — its merge commit is built by `git merge-tree --write-tree` and `commit-tree`, and runs no hook either.
- **A command an unattended run issues must be spellable as a literal.** For a wrapper the script-allowlist guard vouches for — one under the session's own scripts directory — a `$(…)`, a backtick, a pipe, a `<`, a `>` that is not a descriptor duplication or `/dev/null`, or a braced expansion other than a bare `${IDENT}` anywhere in the command string withdraws the guard's permit, as does a `$` in any spelling inside the `.sh` path itself, and the call, left without one, is refused at once in an unattended run (`plugin/hooks/autonomous-script-allowlist-guard.sh`). **A call to a main-checkout wrapper — `commit-on-branch.sh`, `push-branch.sh`, `refresh-branch.sh` and `launch-sandboxed-gates.sh` under `<MAIN_REPO>` — carries no `$` at all**, a bare `${IDENT}` and the commit subject included: from a run copy the guard does not vouch for the main checkout's copy, so the permission profile's literal `allow` entry is the call's only grant, and any shell expansion loses the match (`plugin/instructions/autonomous_pause_and_ledger.md` §1.6; `plugin/instructions/dispatch_discipline_instructions.md` → `## Commit mechanics`; for the launcher, the `<gate_launcher>` row of `plugin/instructions/plan_orchestration_instructions_autonomous.md`).

## Plugin asset authoring

- **Every reference from one plugin asset to another is written `${CLAUDE_PLUGIN_ROOT}/<path>` — except a path a shell body *dereferences*.** Never a relative path, never a path assembled from a version, never a path into a sibling plugin: it is the only form correct under both a git-sourced install and a directory-sourced one, and it interpolates in agent bodies and in a hook's `command` string alike (`docs/development.md` → `## 2. The one authoring rule that follows`). The exception is the token's one dead spot — the runtime substitutes it into a hook's `command` string and does not export it into the resulting `bash` process, so a script that dereferenced it would break the moment anyone ran it by hand. A shell asset therefore resolves a sibling from `${BASH_SOURCE[0]}`, which is the form `## Shared code, and where it lives` above already requires of the sourced library, and it binds every guard and helper script here. Citing the token as **text** — in a header comment naming the asset that invokes this one — is the mandated citation form and is unaffected (`plugin/hooks/README.md` → `## The shared library`; `plugin/scripts/find-free-port.sh` → the `# Used by` line).
- **Every agent definition declares a `tools:` allowlist, and `model: inherit`.** An agent added with no `tools:` field inherits the full default tool set and silently re-opens browser access; a review rejects it. The allowlist is the whole mechanism — a `permissions.deny` backstop on the browser namespaces is forbidden, because a global deny is evaluated before any allow and would revoke the interactive-test agent's own grant (`plugin/agents/README.txt`).
- **`plugin/agents/` and `plugin/commands/` carry `README.txt`, not `README.md`.** Component discovery loads every `.md` file in those two directories as a component, so a `README.md` there fails `--strict` with `frontmatter: No frontmatter block found`. Every other directory that carries a README carries an ordinary `README.md` (`docs/development.md` → `## 3. Manifest facts a contributor must not rediscover`).
- **Add only manifest fields the validator recognizes.** `--strict` promotes an unknown field from a warning to an error, and the marketplace entry deliberately carries no `version` because `plugin/.claude-plugin/plugin.json` is the sole version of record (`docs/development.md` → `## 3. Manifest facts a contributor must not rediscover`).
- **An agent that cannot read a cited contract, sample or instruction file reports it** through its own `error:` / blocker return, naming the path and the refusal, and produces no artifact. A substitution is a finding, not a fallback (`plugin/agents/README.txt`).

## Documents of record

- **A measured fact states what was measured, the command and the exact message**, so a later version that behaves differently is detectable rather than merely surprising (`docs/development.md`, opening).
- **A deferral cites a numbered roadmap item, and the number owes a row.** The legend is `docs/development.md` → `## 6. The roadmap this tree defers to`; a deferral whose numbered roadmap item has no row there is a defect.
- **An engine-level divergence between the two docs-retrieval backends is recorded, never papered over**: it belongs in `docs-retrieval-service/README.md` → `## The seam, as found`, not in a normalised output or a loosened comparison (`docs-retrieval-service/README.md` → **Where byte parity is asserted.**).
- **`examples/notes-app/` is two things with different obligations.** Its run artifacts under `devscene/` and the prose of its `.claude/CLAUDE.md` and of the documents under `.claude/context/` are a **frozen capture** of what the harness produced on a stated date — editing them falsifies the record rather than fixing it, and no criterion introduced after that date grades them. Its own source and toolchain, and every other file `init` rendered into it (`.claude/settings.autonomous.json` among them, re-rendered whenever a token-carrying `cli/templates/` file changes), are **live** and are maintained. Nothing there is a rule for this repository (`examples/notes-app/README.md` → *"The capture is frozen; the fixture is live"*).
- **This repository has adopted its own harness**, so `devscene.config.json`, `.claude/`, `harness-runs/`, `githooks/` and the generated wrappers under `scripts/` at this root are `init`'s output in this checkout. `scripts/` also carries hand-written scripts that `init --force` does not regenerate — `scripts/run-gates.sh` among them (`docs/development.md` → `## 5. Verifying a change`, opening: *"It is hand-written and is not in the set `init --force` regenerates"*). A rule read off `harness-runs/` describes a run, not this project.

## The testing bar

**Each layer's runner is fixed**: Node's built-in `node --test` over `cli/test/*.test.mjs` with `node:assert/strict` for `cli`, whose `pretest` compiles first so **every test runs against the compiled CLI at `cli/dist/cli.js`**; `pytest` over each Python package's `tests/`, run through `scripts/python-service.sh` (`cli/package.json`; `docs-retrieval-service/README.md` → `## Testing`; `graphscene/README.md` → `## Running the toolchain`).

- **No test ever creates a fixture inside this checkout, and no test is ever aimed at this repository.** The `cli` suite builds a throwaway fixture repository under `os.tmpdir()` and tears it down in process (`cli/test/helpers/fixture.mjs`); the Python suites plant files under `pytest`'s `tmp_path` or the system temp directory (`docs-retrieval-service/tests/conftest.py` → *"No fixture is created inside this checkout."*; `graphscene/tests/test_boundary.py` → `_plant`; `devscene-flow-host/tests/test_boundary.py` → `_plant`).
- **The `cli` suite has no mocking framework, and adding one is a decision raised as a `stale-rule` entry for a supervised `/analyze` re-run or a hand edit, never a change an implementing run makes.** Its substitutes are the throwaway fixture repository; a subprocess run of the built CLI whose stdin is a pipe, which exercises the side of every prompt that *cannot* be asked; and constructor-injected sinks where a unit needs its output captured (`ReporterOptions`). The Python layers' substitutes are their own documents' (`.claude/context/docs-retrieval.md` → `## Testing — what "done" means here`; `.claude/context/graphscene.md` → `## Tests`).
- **A test file opens with the rule it exists to enforce**, stated in its header before any case — and where a documented behaviour is deliberately not covered, that header says which behaviour and why (`cli/test/daemon.test.mjs`, `cli/test/init.test.mjs`). In a Python layer the header is the module docstring opening *"The rule this file exists to enforce"* (`docs-retrieval-service/tests/test_cli.py`, `graphscene/tests/test_boundary.py`, `devscene-flow-host/tests/test_graphscene_dependency.py`).
- **Assert against the contract stated literally, not against what generated the output.** The one deliberate inversion is the byte-for-byte comparison in `cli/test/outer-loop-scripts.test.mjs`, where *"copied verbatim, with no substitution"* is itself the contract; its header argues the exception.
- **Where behaviour cannot be reached from a behavioural test, guard the source instead** (`cli/test/prompt.test.mjs` reads `cli/src/core/prompt.ts` and asserts on its text). That is a last resort with its reason written down, not a first move.
- **The verification commands are the ones `devscene.config.json` names**: `commands.typecheck` and `commands.test`, both of which must exit zero. Run a gate **without a pipe** — piping into a pager returns the pager's status, and a failing gate then reads as a passing one.
- **A unit's own verification runs the one test file it created or edited, from the repository root, as one plain foreground command.** In `cli` that is `npm test --workspace cli -- test/<name>.test.mjs`; in a Python layer it goes through `scripts/python-service.sh`, in the form that layer's document gives. Never prefix it with a `cd`, pipe or redirect its output, or start it in the background, in any run mode — a `cd` compound is not a string an unattended run's permission profile allow-lists, so it is refused at once rather than prompting. A run the tool layer moves to the background on its own is not waited on: record it as not run, never a pass. `commands.test` runs every automatable gate and takes no file argument, so it is the change's closing check, not the per-unit one. For `cli`: `--workspace cli` runs the script in `cli/`, the `--` forwards the path to `node --test`, and `pretest` still compiles first. **The output you read back may not be what a terminal shows**: under Node 20 and 22 a captured run prints a TAP summary carrying `# tests <n>`, `# pass <n>`, `# fail <n>`, where a terminal (and a newer Node's default) shows `ℹ tests <n>`. Read the counts and the exit status; never wait for either summary line to appear. Do not narrow the run with `--test-name-pattern`: most cases are `t.test` subtests created at run time inside a parent `test(...)`, so a pattern naming only the subtest skips the parent and reports the file as passing with nothing run (under Node 22.23.2 on `cli/test/init.test.mjs`: `tests 1`, `pass 1` in 80 ms). `--test-skip-pattern`, which could single one out, is refused by Node 20.19.5, which `engines` admits.
- **The full bar is `docs/development.md` → `## 5. Verifying a change`**, whose gates are the definition of done for a change in this tree. That section, not this paragraph, is the authority for how many gates there are and what each one checks; read it before claiming a change is verified. The one split it draws that an implementer needs here is in its opening paragraphs: `scripts/run-gates.sh`, which `commands.test` reaches, runs every gate a process can run without a terminal, a browser, a model session or a network, and prints the rest rather than passing over them — those are hand-run. Some of the gates and legs it runs depend on a provisioned cache, environment or tool — gate 13's Python legs are `BLOCKED` where `uv` or the synced environment is missing — and where that is missing it reports them `BLOCKED` or `SKIPPED` and counts them among neither its passes nor its failures, so a zero exit is not evidence that every automatable gate ran. The `== gates this script cannot run` block it prints on every run, and the closing `run-gates:` line of a run that exits zero, name each gate and leg it did not run; read those, not the exit status.
- **The self-containment gate binds every commit:** nothing in this tree may name a location on the machine that wrote it, and no generator template may have been committed into the adopter's own dot-namespace. A Python package's in-tree environment and tool caches (`.venv`, `.mypy_cache`, `.ruff_cache`, `.pytest_cache`, `__pycache__`) record machine paths and are never committed (`docs/development.md` → gate 6a).

## Commit-message policy

**Subject form:** `<prefix>: <Description>`, at most 72 bytes (`cli/templates/scripts/lib/unit-commit-lib.sh` → `UCL_SUBJECT_MAX`).

**Prefix vocabulary — closed:** `feat`, `fix`, `refactor`, `docs`, `chore`, `research`. Any other token is not a legal `commit_prefix`.

**Per commit class:**

| Commit class | Prefix |
|---|---|
| New work — a story task's commit (row `A`, or the supervised item loop) | The token derived from the branch name (row `A`'s rule). It yields only `feat`, `fix`, `refactor` or `chore`, so a task on a `docs_` or `research_` branch commits as `chore`. |
| A fix to existing work — the review-fix rows' commits | `fix` |
| A user-review fix item (row `UR-A`) | The token its severity mapping names. |
| Restructuring existing work with no behaviour change | `refactor` |
| A change confined to documentation prose, other than a research record | `docs` |
| A research or measurement record under `docs/` | `research` |
| A configuration or housekeeping commit outside the flow | `chore` |
| A run artifact the flow emits on its own behalf | Its fixed form below. |

`none` never arises: every class above carries a token.

**Unit subjects are built, never written.** A unit commit — a story task, a review or test-fix finding, a user-review finding — is made by `scripts/commit-on-branch.sh --unit`, and its subject is `<prefix>: <unit label> — <short title>`, built by `cli/templates/scripts/lib/unit-commit-lib.sh` from the readiness index:

- `<prefix>` is the class's token from the table above (`ucl_unit_prefix`); `--prefix refactor|chore` is taken only for a user-review Should Fix.
- `<unit label>` names the unit and, for a finding, the review it came from, because finding numbers repeat across reviews: `Task 3`, `Code review finding 2`, `Parity review finding 1`, `Architecture review finding 1`, `Skeptic review finding 1`, `QA finding 1`, `Test fix 1`, `User review finding 4` (`ucl_unit_label`).
- `<short title>` is the readiness entry's title with its `_(layer: …)_` / `_(points: …)_` markers removed, `` ` ``, `$`, `|`, `<` and `>` dropped, and cut at the last word boundary that keeps the whole subject within 72 bytes; when no word fits, the title and its ` — ` are dropped (`ucl_short_title`, `ucl_subject`). The unit label always survives.

**A unit's record goes on one body line, never in the subject.** At most one, in this precedence, lower-case: `record disposition of <token> — <cause>`, `mark <token> already passing — <cause>`, or `mark <token> done — <set>` when no work file was staged (`ucl_body_record`). `<token>` is `Task K` or `Finding K`; the cause is read from the `**Cause:** ` line of the unit's detail file, never from a command line. `statistics-plan-writer` and `improvement_observations_instructions.md` read these substrings on any line of the message.

**Capitalisation.** The first word after the prefix is capitalized (`fix: Add foo`, not `fix: add foo`). The built unit subject satisfies it because the unit label leads (`fix: Code review finding 2 — …`); a body record line stays lower-case, and its readers match its leading word case-insensitively.

**Attribution trailers are forbidden** — no `Co-Authored-By:`, no `Claude-Session:`, no trailer naming an agent, a model or a session (`cli/templates/claude/settings.autonomous.json` → `attribution`, which sets `commit` and `pr` empty, and that file's *"COMMIT ATTRIBUTION IS OFF"* comment).

**Merge commits.** A merge commit `refresh-branch.sh` writes is bound by the trailer ban only: its message is `Merge branch '<base>' into <branch>` or `Merge remote-tracking branch 'origin/<base>' into <branch>`, as `git merge` spells it.

**Fixed-form subjects — exempt from the capitalisation rule and the length cap.** Every one a flow commit point emits is declared once, in `cli/templates/scripts/lib/unit-commit-lib.sh` → `ucl_artifact`'s table (with `ucl_review_kind_subject` and `ucl_ui_pass_subject` for the non-ticking units), and reached through `commit-on-branch.sh --artifact <kind>` or `--unit`; the planning driver reads the same table (`cli/templates/scripts/lib/planning-record-lib.sh` → `prl_artifact_commit`). The rest are written by the watcher and the commands that drop inbox files. `<branch>`, `<entry-id>`, `K`, `<n>` and `<k>` are substituted verbatim; re-casing or truncating one breaks the commit point that owns it.

- `chore: Add branch statistics for <branch>`
- `chore: Add flow-progress ledger for <branch>`
- `chore: Add task plan for <branch>`
- `chore: Add UI-test plan for <branch>`
- `chore: Add user-review fix plan for <branch>`
- `chore: add code review for <branch>`
- `chore: add docs checklist for <branch>`
- `chore: add task prompt for <branch>`
- `chore: add user review for <branch>`
- `chore: Commit re-screened input edit for <branch>`
- `chore: Fix plan <n> round <k> for <branch>` and `chore: Fix plan <n> round <k> partial for <branch>` — `plugin/instructions/plan_review_rounds.md` looks the previous round's commit up as `chore: Fix plan <N> round <iteration − 1> for <branch>`; it is the same subject
- `chore: Flow progress <entry-id> for <branch>`
- `chore: Log dispatch additions for <branch>`
- `chore: Log improvement observations for <branch>`
- `chore: Mark UI test K passing for <branch>` — `plugin/instructions/plan_orchestration_instructions_core.md` spells the test number `N`; both are the same subject
- `chore: Plan round <n> for <branch>` and `chore: Plan round <n> partial for <branch>` — `plugin/instructions/plan_review_rounds.md` looks the previous round's commit up as `chore: Plan round <iteration − 1> for <branch>`; it is the same subject
- `chore: Record clarification digest for <branch>`
- `chore: Record lessons for <branch>`
- `chore: Record run analytics for <branch>` — written by the run watcher (`cli/templates/scripts/autonomous-watcher.sh` → `run_analytics_subject`)
- `chore: Update branch statistics for <branch>`

**Re-derive that list, never carry it over:** probe `${CLAUDE_PLUGIN_ROOT}` and `scripts` for `docs`/`feat`/`fix`/`refactor`/`chore`/`test`/`research` subjects carrying a `<branch>` / `$branch` / `${branch}` / `%s` / `<entry-id>` / `K passing` / `N passing` token. A new fixed subject without one of those tokens is outside the probe; widen it. Left out, by class: `chore: add qa review for <branch>` — its flow forbids emitting it (`plugin/instructions/plan_orchestration_instructions_core.md` → *"there is no `chore: add qa review for <branch>`"*); and the worked examples `chore: Add branch statistics for ${branch}` (a comment in `plugin/hooks/autonomous-script-allowlist-guard.sh`) and `chore: Flow progress A1.5f for <branch>` (an `e.g.` in `plugin/instructions/autonomous_pause_and_ledger.md`).

**Changing any fixed subject is a multi-file edit.** Edit its row in `ucl_artifact` (or the script that owns it), both copies of the library (`cli/templates/scripts/lib/` and the self-adopted `scripts/lib/`), and every flow file that quotes it.

## Reference implementation

The seam: what an adapter would have to carry` describes a *hypothetical* second engine with its evidence attached; it is not a reference implementation to match, and nothing in this tree may be held to it.
