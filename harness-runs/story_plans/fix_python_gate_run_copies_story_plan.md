# Story: The Python gates run inside an unattended run's copy

## Context

This branch makes gate 13 (the Python docs-retrieval service, `scripts/python-service.sh`) **run** inside an unattended run's copy rather than grade `BLOCKED` or `FAIL` there. It also lets the wrapper serve more than one Python package, so the GraphScene walker's own package can join it later as one table row, without a second wrapper. Building GraphScene's package, and the gate legs for it, belongs to the later branch that ports the walker. This branch delivers the route that package will take.

**Why it fails today, read from the tree.** A run copy is a clone, created and bootstrapped **unsandboxed** by `scripts/create-worktree.sh` → `scripts/setup-worktree.sh --target <copy>`. Bootstrapping runs the main checkout's `commands.depInstall` (`npm ci`) in the copy, then `commands.build`. The gates then run **sandboxed**: in-session under Claude Code's sandbox on macOS (`.sandbox.filesystem.allowWrite` is the state directory, on top of the session's own working directory), and on a bubblewrap host under `scripts/launch-sandboxed-gates.sh`'s vector (`--ro-bind / /`, `--bind <target> <target>`, a private `--tmpfs /tmp`, `--unshare-all` and so no network). Both sandboxes therefore allow the same writes: **the run copy itself, plus a temporary directory**. Today `python-service.sh` writes the venv to `${XDG_CACHE_HOME:-$HOME/.cache}/devscene-docs-retrieval/venvs/<cksum of the checkout root>`, and the ruff and mypy caches to the same root. `uv` writes its own cache to `~/.cache/uv`. None of those is writable in either sandbox, and no step ever syncs a venv for the copy's key. So an unprovisioned copy exits `3` (`BLOCKED`). A copy synced by hand gets past that check but then fails on `~/.cache/uv` (`FAIL`).

**The decisions this plan takes** (the prompt's leads are starting points; these are what this plan holds to):

1. **Provisioning happens at bootstrap, never in a gate.** `commands.depInstall` becomes `npm ci` followed by a guarded `bash scripts/python-service.sh provision` (Task 3, which spells the full line). The guard runs `provision` only where the bootstrapped checkout's own wrapper carries Task 1's `# PROVIDES: provision` marker line. A checkout on a branch cut before this one, such as a `create-worktree.sh --existing` follow-up run, has a wrapper with no `provision` or no wrapper at all. It prints a `SKIPPED` line and bootstraps as it does today. The line runs unsandboxed with the network, in every mode that bootstraps a checkout: the local watcher's `--target` bootstrap on macOS and Linux, the GitHub job's `Bootstrap the checkout`, and a person's by-hand `setup-worktree.sh`. No gate leg ever reaches the network, so the prompt's "offline sync from the main checkout's cache" lead is not taken: it would need a sandboxed `uv` to lock a cache it cannot write. This adds no new trust class. `setup-worktree.sh`'s header already names the residual: the main checkout's `commands.depInstall` runs in the copy, unsandboxed, and a run-written `package.json` lifecycle entry already reaches arbitrary code through `npm ci`. The new step runs the copy's own `python-service.sh` and `uv sync` (which builds the project from the copy's `pyproject.toml`), both in that same class. Task 6 says so in `docs/development.md`.
2. **Each package's environment and tool caches move into that package's directory**: `<package>/.venv`, `<package>/.ruff_cache`, `<package>/.mypy_cache` (Task 1). That is the one persistent location both sandboxes can write. `uv run` may write into its environment (an environment lock, for one), and a read-only venv under `~/.cache` would fail on that. The location is keyed per checkout by construction, and it goes when the run copy goes, so venvs keyed by dead copies stop piling up under `~/.cache`. All four directory names are already ignored by the root `.gitignore`'s Python block. Gate 6a gains exclusions for them (Task 2), because a venv names the interpreter's `$HOME` path.
3. **The read-only legs run `uv run --frozen --no-sync --no-cache`** (Task 1). `--no-sync` installs nothing, so a per-checkout `uv` cache would hold nothing worth keeping. `--no-cache` puts whatever `uv` writes into a temporary directory under `$TMPDIR`, which both sandboxes can write. That is this plan's answer to the prompt's first lead. `lock` and `sync` keep the machine's shared `uv` cache: they run unsandboxed, and a warm shared cache is what makes a per-copy sync quick.
4. **A host with no `uv` still grades `BLOCKED`.** `provision` exits `0` with a printed `SKIPPED` line when `uv` is not on `PATH`, so a Python-less host still bootstraps, and the legs then exit `3` as today. If `uv` is present and a sync fails, `provision` exits `1`, which fails the bootstrap the same way a failed `npm ci` does.
5. **The wrapper serves a closed package table**, selected with `--package <dir>`. Today the table has one row, `docs-retrieval-service`, and it is the default, so every existing `bash scripts/python-service.sh <sub-command>` call keeps its meaning (`README`s, `docs/retrieval-eval.md`, `evals/docs-retrieval/python-backend.mjs`, `docs-retrieval-service/src/devscene_docs_retrieval/models.py`'s message). `provision` covers the whole table and takes no `--package`.

**Every execution mode is covered by the same two changes**, because each sandbox allows the same writes and each mode bootstraps through `setup-worktree.sh`. This repository commits no run-job workflow (`.github/workflows/` holds `publish-main.yml`, `release-npm.yml` and `supply-chain.yml`), so job mode is reached only once one is rendered. A job host without `uv` then grades `BLOCKED`, per decision 4.

**Ship order.** Contract before consumer: the three script and configuration tasks under the catch-all `general` layer come first (Tasks 1–3). The two `cli` suites that pin them follow (Tasks 4–5). The catch-all documentation task comes last (Task 6). This puts `cli` after `general` for the test tasks, because a suite cannot pin a wrapper that does not exist yet. `harness-runs/story_plans/feat_gate_timings_failed_first_story_plan.md` orders its repo-local scripts and their suites the same way.

**Top risks:** The first risk is a `uv` write inside the sandbox that this plan did not foresee, which would turn `BLOCKED` into `FAIL` again. Task 1 guards it by routing every write the wrapper controls into the package directory or `uv`'s own temporary cache. Task 4 asserts that a leg run leaves `HOME` untouched. The real-shape evidence is gate 13 itself, in the first run copy bootstrapped after this branch merges. This branch's own copy was bootstrapped with the old `depInstall`, so its Run gates round still grades gate 13 `BLOCKED`, and that is expected, not a regression. The second risk is a bootstrap that refuses a whole run: on a host without `uv`, on a sync the host could not complete, or on a checkout of an older branch whose wrapper has no `provision`. Task 1's `provision` exit contract and its `# PROVIDES: provision` marker guard the first two, and Task 4 pins both. Task 3's marker test in the configured line guards the third, and Task 3's Verification runs that line against a checkout carrying today's wrapper and one carrying none. The third risk is the in-tree environment leaking `$HOME` into gate 6a or into a commit. Tasks 2 and 5 guard it.

**Manual setup required:**

- After this branch merges, run `bash scripts/python-service.sh provision` once in the main checkout, and in any working copy you made by hand, from an ordinary unsandboxed terminal. The environment now lives at `docs-retrieval-service/.venv`, and the old one under `~/.cache/devscene-docs-retrieval/venvs/` is no longer read, so until then gate 13 grades `BLOCKED` in a hand run there. Depends on Task 1.
- Confirm that `uv` resolves on the `PATH` the run daemon was installed with: `daemon install` captures the installing shell's `PATH` (`cli/src/daemon/units.ts`, point 5). Where it does not, every run copy's `provision` step prints its `SKIPPED` line and gate 13 keeps grading `BLOCKED`. Re-run `daemon install --force` from a shell where `uv` resolves. Depends on Task 3.
