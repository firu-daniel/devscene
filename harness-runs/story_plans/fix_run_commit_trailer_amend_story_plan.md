# Story: Stop an unattended run from splitting its branch with a trailer and a raw amend

## Context

This branch closes the two defects behind the `feat_network_refusal_report` park: a run commit that carried an attribution trailer the adopter's commit-message policy forbids, and a raw `git commit --amend` in the run copy that moved only the run copy's `refs/heads/<branch>`, leaving the main checkout's on the original commit until a person repaired it with `git update-ref`. It delivers the task prompt's three goals in seven single-layer tasks, in the configured layer order — `cli`, then `plugin`, then the catch-all `general` last. Within a layer, a task that creates a fact ships before any task that cites it: the run copy's ref rows (Task 1) before the profile text that describes them (Task 2), and the rows of record (Task 6) before the docs that cite them (Task 7).

**How the task prompt's five proposals were settled, against the code.**

- **Switch off Claude Code's commit attribution in the run profile — taken (Task 2).** Every launch path passes the profile through `--settings`: the run watcher renders a per-run copy from `cli/templates/claude/settings.autonomous.json` and passes it at every spawn, and job mode passes the base unchanged (`cli/templates/scripts/autonomous-watcher.sh` → `run_profile_render`, the `JOB MODE` header, `spawn_engine`'s `--settings "$settings_file"`). The key is written in its object form, `"attribution": {"commit": "", "pr": ""}`, and never as `false`. The `false` form needs Claude Code v2.1.281 or later, and an older version skips the whole settings file holding it. A `-p` session ignores an invalid settings file silently, which `docs/sandbox-record.md` residual 11 records. So the `false` form, on an older Claude Code, would start a run with no sandbox block and no `deny` rules. Task 2 does not delete the adopter's own trailer rule. It removes the instruction that produced the trailer, and `<commit_conventions>` still decides whether a trailer is wanted. The template `cli/templates/claude/context/conventions.md` keeps its statement that the harness takes no position on trailers.
- **Make the commit wrapper refuse a trailer — not taken.** The adopter's trailer policy is prose in a conventions document. The template says some projects require a trailer on every agent-assisted commit and others forbid one. A generic wrapper has no way to read that prose. Giving it one would need a new `devscene.config.json` key, which is the four-place contract of `.claude/context/conventions.md` → `### The order files are created…`. A wrapper that refused trailers unconditionally would break the adopters whose policy requires one. Task 2 closes the cause, and Task 5 makes the committer check the commit that actually landed and report one that went wrong.
- **Permission layer — taken, narrowly (Tasks 2 and 4).** No flow needs a raw `git commit` in an unattended run. Every commit point goes through `commit-on-branch.sh` (derived by `git grep -n "git commit" -- plugin`). So Task 2 drops `Bash(git commit:*)` from `allow` and adds the deny `Bash(git commit --amend:*)`. That alone would not hold, because `plugin/hooks/git-commit-branch-guard.sh` today emits `allow` for the **whole command** whenever its first commit piece is on an ordinary branch, judging no other piece, and *"a hook `allow` short-circuits the permission system"* (`docs/guard-verification.md` row WK30). So today `git commit -m x && git commit --amend -m y`, or a commit followed by `git reset --hard`, `git update-ref` or `git rebase`, is guard-allowed. Task 4 closes that: the shared library's `hc_piece_is_never_safe` refuses a `commit` piece carrying `--amend`, and the commit guard judges **every** piece and withholds its `allow` — only its `allow`; its `ask` on a protected branch, a detached HEAD or an unresolvable configuration is unchanged — when any piece rewrites a commit, is a git call outside its remit (`commit`, `add`, `status`, `diff`, `log`, `show`, `rev-parse`, `ls-files`), is a non-git command other than a leading `cd`, or carries a pipe, redirection or substitution.
  - **What the permission layer then refuses, under `dontAsk`.** A raw `git commit --amend` (the new `deny`); `git update-ref` (in neither `allow` nor `ask`); `git reset` and `git rebase` (on `ask`). Each is refused standing alone, and, after Task 4, no guard admits one beside a commit: the commit guard withholds its `allow`, and `allow-safe-compounds.sh` admits none of them because none is in `hc_safe_prefixes`. `git commit --fixup` makes a new commit forward and rewrites nothing.
- **Sandbox layer — taken (Task 1), as the floor that holds for every spelling.** The permission layer judges command strings only. `scratch-run.sh` runs any file the session wrote, sandboxed, and a plain `git commit` stays guard-allowed. So the only layer that covers every spelling is the OS one. Task 1 adds three rows to `cli/src/generators/writeProtection.ts` → `COPY_GIT_PATHS` — `.git/HEAD` (`file`), `.git/refs/heads` (`directory`) and `.git/packed-refs` (`file`) — each with `bubblewrapDenyWrite: true`, and adds the same three to the watcher's declared mirror `RUN_PROFILE_COPY_GIT_PATHS`.
  - **How the paths are spelled.** The per-run copy carries the run copy's exact path, so the Linux glob behaviour of AP2 and GW1 does not reach the run's own copy. The base keeps the sibling-glob form, as every other row of that table does. Job mode is unaffected: its run copy is the main checkout, whose whole `.git` the base already write-denies.
  - **What it costs.** The flows' sandboxed git in a run copy is `git status`, `git add`, `git diff` and `git log`. Those write the index and objects only, and keep working. `git commit`, `git switch` and branch creation are meant to fail. `git stash push` is expected to fail too: derived, not measured, it runs `git reset --hard`, which locks `refs/heads/<branch>`. No flow and no session-run script issues any of the four (derived by grep across `plugin/` and `cli/templates/scripts/{run-test-suite,flow-walker,prompt-injection-screen,scratch-run,launch-sandboxed-gates}.sh`).
  - **How it relates to the permission layer.** It backs that layer up and does not replace it. The new protection is graded `owed` (Task 6's row CS16) until a probe measures it, so the permission layer is the measured fast-feedback layer for the incident's own spelling.
- **Committer contract — taken (Task 5), and the flow parks.** After the wrapper commits, the committer reads back the commit that landed. One that landed wrong is returned as an `error:` naming the commit and what is wrong, and is never amended, reset or recommitted. Every caller already maps a committer `error:` to `<escalate>` (`plugin/instructions/plan_orchestration_instructions_core.md`, `plugin/instructions/user_review_fixes_instructions_core.md`), so an unattended run parks. A retry through a wrapper is not taken: no wrapper rewrites a landed commit while keeping both refs in step, and adding one would be a ref-rewriting route of exactly the kind this branch removes. The orchestrator's own direct wrapper commit points take the same rule in `plugin/instructions/autonomous_pause_and_ledger.md` §1.6.

**Goal 3 — the split is named plainly, with its repair (Task 3).** When the two tips diverge, every wrapper and the watcher's copy check refuse, and the refusal sentence comes from one place: `cli/templates/scripts/lib/harness-run-lib.sh` → `hr_copy_sync_in_var`'s diverged arm. That sentence reaches a park through the committer's `error:`, `push-branch.sh`'s `refusing to push:` line and `HR_RUN_REFUSAL`. Task 3 rewrites that one sentence, which still contains `have diverged`. When the two tips share a parent, it says one rewrote the other outside the wrappers. It names both full commit ids and gives the two `git update-ref` repair commands, the one the maintainer used for Park 1 and its mirror.

**Cross-task interfaces.**

- Task 1's three new rows are `['.git/HEAD', 'file']`, `['.git/refs/heads', 'directory']` and `['.git/packed-refs', 'file']`, appended in that order after `.git/objects/info/http-alternates`. Tasks 2, 6 and 7 cite them by those paths.
- Task 2's profile shape is: the `attribution` key equal to `{"commit": "", "pr": ""}`; no `Bash(git commit:*)` in `permissions.allow`; `Bash(git commit --amend:*)` in `permissions.deny`; and a **FOUR COMMANDS…** `_README` clause saying the per-run copy also refuses a sandboxed move of the clone's own ref (derived, owed until CS16).
- Task 4's library contract: `hc_piece_is_never_safe <piece>` returns 0 for a `git … commit` piece that carries `--amend` in any abbreviation git accepts, or that carries a `$` or a backtick. The commit guard's contract is the sixteen-row table in `task_4_plan.md`, which Task 6 restates and records: on an ordinary branch it is silent instead of `allow` when any piece fails the remit test; on a protected branch or a detached HEAD it still asks.
- Task 6's rows of record, cited by Task 7: AT1, AT2, CS16, CS16 (Linux) and PD32 in `docs/sandbox-verification.md`.
- Task 5's named return is `error: commit <short_sha> landed wrong — <what is wrong>; not repaired`.
- Task 3's refusal keeps the substring `have diverged`, which `cli/test/clone-sync.test.mjs` and `cli/test/wrapper-clone-arm.test.mjs` match on.

**What this branch does not change.** The adopter's commit-message policy and its template. The commit wrapper's message handling. The flow sentences saying the caller passes no trailer and the wrapper adds none (`## Scope register`, rows 4–11). The sandbox probe's CS3 leg: CS16's probe leg is owed under roadmap item 21, and Task 6 records why.
**Top risks:**

- **A legitimate sandboxed git call breaks.** The new ref write-deny could refuse a sandboxed call some flow or adopter relies on. `git stash push` is the likeliest. On a bubblewrap host it could also mount a placeholder at an absent `.git/packed-refs`. Task 1 limits the rows to the ref store and HEAD. Task 6 adds the owed row CS16 that measures it on macOS and Linux, and Task 7 states the cost in `docs/sandbox-record.md`. Until CS16 is taken, the probe's CS3 leg will report `fail` for its `commit`, `stash push` and `switch -c` calls. Task 6 records that as PD32, so the next probe run is read correctly rather than as a regression.
- **The permission layer does not hold.** A plugin guard's `allow` covers the whole compound and bypasses the profile. Task 4 closes it for an amend in any piece and for any piece outside the commit guard's remit, while keeping every `ask` the guard gives today. Task 4's REPRO reproduces the silent and `ask` outcomes, and Task 6 records all sixteen decisions in `docs/guard-verification.md`.
- **The fix never reaches this repository's own runs.** This repository runs its root `scripts/` copies and its untracked `.claude/settings.autonomous.json`, and neither is rewritten by any task here. `Manual setup required` lists the supervised re-render.
