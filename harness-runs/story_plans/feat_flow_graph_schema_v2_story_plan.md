# Story: Flow graphs declare their own vocabulary — the generic format-4 schema in `graphscene/`, with the harness's format-3 graph generated from it

## Context

`schemas/flow-graph.schema.json` (format 3) builds the harness's names in as closed lists: the outcomes (`dispatchNode` → `outcomes.propertyNames.enum`), the phases (`skipEntry` → `phase.enum`), the bindings (`bindingName.enum`, `bindingEdge` → `binding.enum`, `escalateEdge` → `reason.enum`) and the round's `PASS`/`FAIL` (`roundNode` → `outcomes.required`). `cli/templates/scripts/flow-walker.sh` also gives several of those names fixed behaviour: `<ask>` parks and resumes only with `answered` (the `refuse "outcome '$A_OUTCOME' is not declared while an <ask> is pending …"` line), a gate's `error`/`blocker` is held until the round's other gates finish (`round.held.<gate>`), a skipped node is left out of `roundCounts` (`add_skipped_node`), and a round routes on `PASS`/`FAIL`. This branch adds a **generic format 4** in which each graph declares its own names and maps each one to an engine primitive. The engine routes on the primitive and never on the name.

**What is decided, and where it lands.** These hold for every task:

- **The generic schema lives in `graphscene/`**, as package data at `graphscene/src/graphscene/schemas/flow-graph.schema.json`, so it moves with the library when the library is extracted. The harness reads it from there: the root npm scripts validate against that path (Task 5).
- **The bash walker stays on format 3**, and so do `scripts/check-flow-graph.sh`, `cli/test/agent-return-schemas.test.mjs` and the `validate:flow-graph*` npm scripts. `schemas/flow-graph.schema.json` and its fixtures under `schemas/negative/` and `schemas/flow-graph-check/` are not edited. The harness's planning graph is now **authored** in format 4, at `cli/templates/scripts/flows/task_plan_writing.v4.graph.json` (Task 1), beside the harness's other graphs as the task prompt's lead places the harness vocabulary. Both committed v3 copies — `cli/templates/scripts/flows/task_plan_writing.graph.json` and the self-adoption copy `scripts/flows/task_plan_writing.graph.json`, byte-identical today (blob `8c4f4032`) — are **generated** from it by a harness-side script, `scripts/generate-flow-graph-v3.mjs` (Task 4). Gate 3 holds the committed copies equal to what the script generates (Task 5). This lasts until the cutover, which the GraphScene row of `ROADMAP.md` lists under *Left:* (Task 6).
- **The v4 source is not shipped to adopters.** `cli/src/generators/outerLoopScripts.ts` → `OUTER_LOOP_SCRIPTS` gets no row for it, so `init` never writes it. Its name, `task_plan_writing.v4.graph.json`, cannot be a flow id (`schemas/flow-graph.schema.json` → `identifier` is `^[a-z][a-z0-9_]*$`), so the walker's `<this script's dir>/flows/<flow>.graph.json` lookup can never resolve to it. It does sit inside the npm tarball, because `cli/package.json` → `files` carries all of `templates`. That is accepted: inert data that `init` never writes is not "shipped to adopters".
- **The review-loop keys are carried over unchanged:** `findingsFolder`, `prompts`, an edge's `prompt`, and a round's `writer`, `convergingFrom`, `revisionNote` and `plan`. So are the keys that were never closed lists: `agent`, `heartbeat`, `counters`, `paths`, `reports`, `entries`, `start`, an edge's `increment`/`reset`/`ledger`/`report`, and an escalation's `summary`/`roundCounts`/`evidence`.
- **Node kinds stay engine vocabulary.** `dispatch`, `round` and `terminal` remain a closed enum in the format-4 schema. A graph could declare a new kind but could not give it behaviour, and planning turned up no reason to let it.
- **The vocabulary block** (format 4, top level, after `description`). This is the contract Tasks 1–4 share, spelled once here:
  - `vocabulary.outcomes` — `{ "<outcome>": { "verdict"?: "pass" | "fail", "held"?: true } }`. An outcome name matches `^[A-Za-z][A-Za-z0-9_]*$`. An entry carries at most one of the two keys. A round's join reads `verdict` (it routes on the outcome declaring `pass` or the one declaring `fail`) and `held` (that outcome is held until the round's other gates finish). `{}` declares a plain outcome.
  - `vocabulary.bindings` — `{ "<binding>": { "primitive": "interrupt", "resumeOutcome": "<name>" } | { "primitive": "stop", "reasons": ["<name>", …] } | { "primitive": "end" } }`. A binding name matches `^<[a-z][a-z0-9_]*>$`. The primitives are the engine's and form a closed enum. An `interrupt` parks the walk, and the walk resumes with `resumeOutcome` at the edge's `resume` node. A `stop` ends the walk with one of its declared `reasons`. An `end` finishes the walk and is taken only by a terminal node.
  - `vocabulary.predicates` — `{ "<predicate>": { "records": "<status>", "inRoundCounts": <bool> } }`. A predicate name matches `^[a-z][a-z0-9_-]*$` and a status matches `^[a-z][a-z-]*$`. The host answers each predicate true, false or "cannot answer", and "cannot answer" refuses. The graph never reads configuration. A skip whose predicate holds dispatches nothing, and a round's join counts the skipped node as passed. `records` is the status the walk records for the node, and `inRoundCounts` says whether a cap escalation's round counts keep it.
  - A skip entry becomes `{ "when": "<predicate>", "to": "<node>", "report"?: {…} }`, still evaluated in order. The `construct`/`phase`/`runModeId` keys are gone from format 4.
  - A round node's `outcomes` has exactly two keys, which are declared outcome names: the one whose vocabulary entry declares `verdict: pass` and the one declaring `verdict: fail`. A binding edge is `{ "binding", "resume"?, "reason"?, "summary"?, "roundCounts"?, "evidence"? }`, an `onCap` is `{ "binding", "reason", "summary"?, "roundCounts"?, "evidence"? }`, and a terminal node is `{ "kind": "terminal", "binding" }`.
- **Used names checked against declared ones.** JSON Schema draft-07 cannot take an enum from the document's own data, so this check cannot live in the schema. It lands in `graphscene/` as a stdlib-only module, `graphscene.vocabulary` → `vocabulary_violations` (Task 3), tested on generic fixtures. The format-4 equivalents of the v3 negatives `flow-graph-schema-unknown-outcome.json`, `-unknown-binding.json` and `-ask-without-resume.json` are **schema-valid** and rejected by that check. A loader or a static checker can call it later; this branch builds neither. On the harness side, `scripts/generate-flow-graph-v3.mjs` maps every name it uses through the vocabulary, so it refuses a name it cannot map. Mapping predicates back to `phase`/`runModeId` and primitives back to the fixed v3 names is harness knowledge, and it stays in that script, outside `graphscene/`.

**The harness's own predicate names** (Task 1 declares them and Task 4 maps them; the per-task files repeat this table): `phase_parity_off` and `phase_qa_off` record `skipped` with `inRoundCounts: false` (v3 `construct: skipped`, `phase: <x>`). `run_mode_skips_parity`, `run_mode_skips_architecture` and `run_mode_skips_qa` record `passed-by-exclusion` with `inRoundCounts: true` (v3 `construct: passedByExclusion`, `runModeId: <id>`).

**The layers and the ship order.** The ship order follows `devscene.config.json` → `layers` — `cli`, `plugin`, `docs-retrieval`, `graphscene`, then the catch-all `general` last — and no task touches `plugin` or `docs-retrieval`. Task 1 (`cli`) authors the v4 source against the format spelled above, which is why that format is stated here in full rather than left to Task 2. Tasks 2–3 (`graphscene`) build the schema and the vocabulary check. Tasks 4–6 (`general`) build the generator, wire the gate legs and document the result. `graphscene/src/graphscene/` must stay generic: no harness name, no `devscene` literal and no configuration path in the schema or the module (`.claude/context/graphscene.md` → `## What it may depend on`).

**Top risks:** the first risk is the committed v3 bytes changing. `docs/flow-graph-walker.md` records `wc -c` of that file as a measured fact, and `init --upgrade` replaces every adopter copy whose bytes differ. So Task 4's printer must reproduce the existing v3 files byte for byte, and its `--check` against the unedited committed copies is its acceptance. The second risk is a harness name leaking into the generic schema, so that the library is not in fact generic. Task 2's `test_flow_graph_schema.py` asserts that the schema carries none of the harness's outcome, binding, phase or reason names, and Task 2's own generic fixture uses none of them. The third risk is a format-4 fixture or graph that nothing runs. Task 5 wires every fixture Tasks 2–3 create into a named npm script and a `scripts/run-gates.sh` leg, and lists them by name rather than by glob.
