## Must Fix
1. **`task_3_plan.md` — a Work item asks for a commit-body record that no implementer can write**
   Task 3's third Work item tells the implementer to put the behaviour-to-suite map in the commit body. A task unit's commit has no such channel. The body is built by `commit-on-branch.sh --unit`, and `cli/templates/scripts/lib/unit-commit-lib.sh` → `ucl_body_record` writes a body line in only three cases: `record disposition of …`, `mark … already passing …`, or `mark … done …` for a unit with no staged work. A unit with staged work, which Task 3 is, gets no body line at all (the function returns 1). `layer-implementer`'s return (`plugin/schemas/layer-implementer.return.json`) has only `outcome`, `cause`, `flags` and `blocker`, with no body field. So this checkbox cannot be completed. The only lever that does reach a body line is a `## Disposition` or a `cause`, and either one would record the task as dispositioned or already passing, which is wrong. The story index's first `Top risks:` entry rests on this statement: *"Task 3 retires a suite only together with a statement of which of Tasks 19–21 re-pins each behaviour"*.
   **Raised against:** `- [ ] Record where each behaviour goes, in the commit body's record line. The commit step builds the subject.`
   **Must hold:** Every Work item in a per-task file is one the implementer can complete through its own targets and its return contract. The retired-suite-to-replacement map lives in an artifact that is actually written and committed.
   **Class:** Wrong build
   **Failure:** If the implementer of Task 3 does the Work item "Record where each behaviour goes, in the commit body's record line", then it cannot: `ucl_body_record` writes no body line for a unit with staged work and the implementer's return has no body field. The item stays unfinishable, Task 3's commit carries no behaviour map, and the only levers left (`## Disposition` or a `cause`) would mis-record the task.
   **Fix:** In `task_3_plan.md`, drop "in the commit body's record line" and turn the bullet into plain plan text. The map it lists (`planning-subjects-drift` → none, and why; `PNL_CORE_BLOCKS` → `test_core_agreement.py` check 10; session judgement and agent flags → `test_session_stream.py` / Task 14's `test_agent_flags.py`; walk → Task 19; control → Task 20) is then recorded by `task_3_plan.md` itself, which the plan commit already lands. Alternatively, move the per-case mapping into the replacement suites' headers in `task_19_plan.md` / `task_20_plan.md` / `task_21_plan.md`, which those tasks write. Point the index's first `Top risks:` entry at whichever artifact holds it.

2. **`task_17_plan.md` (producer) / `task_21_plan.md` (consumer) — the return-field constants Task 21 imports are never defined by Task 17**
   Task 21 builds its `(node, field)` pairs *"from `host/run_exits.py`'s field constants and node names, imported rather than retyped"*. Its `**Depends on:**` says *"each field name a module-level `Final` constant there"*. `task_17_plan.md` defines no such constant. It names no constant for `questions`, `tasks_count`, `tests_count` or `reason`, and none for the nodes they are read from. Its only constants rule is the Verification line *"Every literal the module narrates or writes is a module-level `Final`"*, which covers narrated or written text, not the keys it reads out of a return document. The pairing is undefined on the producer side as well. Task 17 reads `questions` from `sessions.return_document(exit.node)`, the `Interrupt`'s own node, so there is no fixed node for it to export. Task 21 meanwhile lists `questions` against `plan_writer` / `ui_writer`. Task 21's own boundary forbids filling the gap from its side: *"It changes no schema and no driver code."*
   **Raised against:** Task 21: `Task 17. host/run_exits.py reads those fields from sessions.return_document(node), each field name a module-level Final constant there.` Task 17 defines no such constant.
   **Must hold:** A cross-task interface is spelled out on both sides. The producer's file defines the exact names (and, for `questions`, the node set) the consumer imports, and the consumer restates those same names.
   **Class:** Wrong build
   **Failure:** If the implementer of Task 17 follows its file and reads the return fields as inline keys (nothing in `task_17_plan.md` asks for field or node constants), then the implementer of Task 21 cannot build `_READS` by importing them without editing `host/run_exits.py`, which `task_21_plan.md` forbids, and so cannot finish the task as written.
   **Fix:** In `task_17_plan.md`, add the exported names to the Work items: one `Final` per field read (for example `QUESTIONS_FIELD`, `TASKS_COUNT_FIELD`, `TESTS_COUNT_FIELD`, `REASON_FIELD`). Add one `Final` tuple of the `(node, field)` reads the module makes, naming the writer nodes whose `Interrupt` it reads `questions` from (`plan_writer`, `ui_writer`). In `task_21_plan.md`, restate those exact names in `**Depends on:**` and `_READS`.

## Should Fix
1. **`task_13_plan.md` / story index — the run log is silent for each node session's whole length, and the watcher's stall watchdog measures liveness from it.** `cli/templates/scripts/autonomous-watcher.sh` → `check_stalled_runs` takes liveness from the newest mtime of `log_path` and `${log_path%.log}.stream.jsonl`. It warns at `STALL_WARN_SECS` (1200 s) and kills the process tree at `STALL_KILL_SECS` (2700 s) unless the tree is at `STALL_BUSY_CPU_PCT` (1 %) or more. The bash pilot kept both files live: `pnl_launch` piped each session through `tee "$stream" | "$PD_FORMATTER" >>"$log_path"`. Under the plan, `ClaudeExecutor` hands the stream over only when `run` returns (`SessionUsage.stream`), and `NodeSessions.record` writes the log and the run stream only then. So a long writer or gate session leaves both files untouched for its whole length. `NODE_INACTIVITY_LIMIT_SECONDS` (2685) was sized against a log that moved with the stream. The kill depends on the CPU guard, which is not verified, so this is not graded Must Fix. Have the driver keep the run log live during a set — for example a periodic `[plan-drive]` heartbeat line while any session is running — or record why the watchdog cannot fire, and pin it in Task 16 or Task 20.
