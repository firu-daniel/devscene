That writes a record under the main checkout's `.git/harness-push-refusals/`. Its header states that the workflow refusal *"records the reason without the path through the same record"*, which *"the watcher's pass reads to stop the run"*. `cli/templates/scripts/autonomous-watcher.sh` → `PUSH REFUSALS (check_push_refusals)` says what happens next: *"this script acts on every record alike, whatever its reason, never parsing it: the run goes `failed` with `push refused: <reason>` … The tick pass is the only site that tears a session down"*. That requirement is still not met by any route the harness takes. The **`<commit_call>`** passage the plan cites (*"never escalated"*) covers only the orchestrator's own handling. It does not cover the watcher's push-refusal pass.
   **Raised against:** story index `## Context` → **The workflow push.**: "**A refused push therefore parks nothing by itself.** The park is Task 6's job." `task_5_plan.md`: "**This task does not park the run, and neither does the refused push.** The park belongs to **Task 6**, which this commit hands off to."

The route must make the unit-`blocker` park happen **before** any push whose send range holds the workflow commit. One way is to move the check-and-park unit ahead of the workflow edit's commit. 2. **Manual step 2 pushes from the run copy, which can neither push as written nor clear the refusal — story index (`chore_rename_devscene_runtime_story_plan.md`) and `task_6_plan.md`**
   Step 2 tells the maintainer to work in the run copy and *"push the branch yourself with a plain `git push` to the remote it tracks"*. Task 6's blocker line repeats this (*"push the branch with git push to the remote it tracks"*). In a clone-per-run copy, which the plan names as the case it serves, the branch tracks no remote. The clone's `.git/config` is held to an allow-list that has no `branch.<branch>.*` key (`cli/templates/scripts/lib/harness-run-lib.sh` → `hr_clone_config_spec`; this run copy's own `.git/config` carries only `core`, `remote "origin"` and `user`). So a plain `git push` there stops with git's *"has no upstream branch"* error. Git's suggested `git push --set-upstream origin <branch>` would write `branch.<branch>.remote` and `branch.<branch>.merge` into the clone's `.git/config`. `hr_clone_config_check_var` then refuses those keys as *"which the clone allow-list does not hold"*. Its caller, `hr_clone_target_check_var`, is the clone check that `commit-on-branch.sh` and `push-branch.sh` both apply, so every later wrapper call against the copy is refused. Even an explicit `git push origin <branch>` from the copy moves only the **clone's** `refs/remotes/origin/<branch>`. `push-branch.sh` computes the commits to send in the **main** checkout: `git -C "$main_top" … rev-list "refs/heads/$branch" --not "refs/remotes/$remote/$branch"`. The main checkout's ref is still stale, so the workflow commit stays in the next send range, and the next unit's push is refused again and writes another refusal record. The plan's sentence *"After the maintainer's push, the workflow commit is no longer among the commits `push-branch.sh` sends"* does not hold for a push made from the run copy.
   **Raised against:** story index manual step 2: "push the branch yourself with a plain `git push` to the remote it tracks (depends on Tasks 5 and 6) … Pushing from that checkout updates its remote-tracking ref, which is what Task 6 re-checks."
   **Must hold:** Each manual step's command succeeds as written in the checkout it names. It leaves that checkout's configuration inside the clone allow-list. It also moves the ref `push-branch.sh` reads (the main checkout's `refs/remotes/<remote>/<branch>`), so the run's later pushes do not see the workflow commit as unsent.
   **Class:** Wrong action from operative text
   **Failure:** If the maintainer runs `git push` in the run copy as manual step 2 says, then git exits with *"has no upstream branch"*. If the maintainer follows git's `--set-upstream` hint instead, the clone's `.git/config` gains off-list `branch.*` keys and every later `commit-on-branch.sh` / `push-branch.sh` call against the copy is refused. Either way, the main checkout's remote-tracking ref stays behind, and the next unit push is refused again on the same workflow commit.
   **Fix:** In the story index's manual steps 1–2 and in `task_6_plan.md`'s blocker line, replace "a plain `git push` to the remote it tracks" with a push that names its remote and refspec explicitly and does not set upstream in the clone. Also say how the main checkout's `refs/remotes/origin/<branch>` comes to include the pushed tip, for example a `git fetch origin <branch>` in the main checkout. Cite the `push-branch.sh` header paragraph that makes this necessary. Re-check Task 6's **Push check** against whichever ref the run's next push actually reads.
