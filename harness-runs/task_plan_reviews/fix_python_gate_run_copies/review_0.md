## Must Fix
1. **`task_3_plan.md` — the new `commands.depInstall` line fails the bootstrap of every run copy whose branch predates `provision`**
   `scripts/setup-worktree.sh` → `run_configured` reads `commands.depInstall` from the **main** checkout's `devscene.config.json`. It then `eval`s that line in a subshell `cd`'d to the copy, so the relative `bash scripts/python-service.sh provision` runs **the copy's own** wrapper. Task 3's own "How the bootstrap reaches it" paragraph says the same. Once this branch merges, the main checkout's line names `provision`. But `scripts/create-worktree.sh` → `--existing` ("recreate a working copy for a branch whose original one was removed (a merged-and-cleaned-up branch coming back for a follow-up run)") clones an **existing** branch at its own tip and bootstraps it. Any such branch cut before this merge carries today's `scripts/python-service.sh`, whose `case` has no `provision` arm. It falls to `*)`, prints `python-service: unknown sub-command 'provision'` and exits `2`. A branch older than the wrapper itself fails with `bash`'s exit `127`. `run_configured` returns 1, `deps_ok=0`, and `setup-worktree.sh` exits non-zero ("bootstrap finished with failures"). Task 3's file says `create-worktree.sh` then removes the copy. The GitHub job's `Bootstrap the checkout` on such a branch fails the same way. The plan does not name this case anywhere: decision 1, `Top risks:` and Task 3 discuss only this branch's own copy ("bootstrapped with the old line") and the no-`uv` host.
   **Raised against:** "`devscene.config.json`: set `commands.depInstall` to `npm ci && bash scripts/python-service.sh provision`."
   **Must hold:** The bootstrap line Task 3 configures lets a checkout whose `scripts/python-service.sh` has no `provision` sub-command (or no wrapper at all) bootstrap as it does today, in every mode that runs `setup-worktree.sh` (the watcher's `--target` in default and `--existing` modes, and the job's and a person's no-argument run). Alternatively, the plan raises the case as a question to the user before it ships (`harness-runs/lessons.md` → *"Leaving a mode out is a question to the user before the plan ships, never a documented residual."*). Whichever is chosen, Task 3's Verification exercises it.
   **Class:** Wrong behaviour
   **Failure:** If the watcher runs `create-worktree.sh --existing` after this branch merges, for a branch cut before it (a follow-up run on a merged-and-cleaned-up branch), then `setup-worktree.sh` evals `npm ci && bash scripts/python-service.sh provision` against that copy's old wrapper, which exits `2` with `unknown sub-command 'provision'`. The dependency install fails, the bootstrap exits non-zero, the copy is removed and the run never starts.
   **Fix:** In `task_3_plan.md`, either make the configured line skip `provision` when the copy's wrapper does not offer it, or route provisioning through a step that is a no-op on such a checkout. Spell the line out so it stays a single string `setup-worktree.sh` can `eval`. Add a Verification bullet that states the expected outcome against a checkout carrying today's wrapper. Restate the chosen line in `task_6_plan.md`'s Task 3 contract, and in the story index's decision 1, if its wording changes. If the choice is instead to refuse such branches, raise it as a question rather than planning it silently.
