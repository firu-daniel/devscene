## Must Fix

1. **`task_4_plan.md` (and the story index `fix_run_commit_trailer_amend_story_plan.md` → `## Context`, the **Permission layer** bullet) — the commit guard's `allow` still covers a compound carrying an amend or another ref move**
   `plugin/hooks/git-commit-branch-guard.sh` walks the compound, keeps the **first** piece whose subcommand is `commit` (`commit_piece="$p"` … `break`), and then emits `allow` for the **whole command**. It judges no other piece. Task 4 only adds `hc_piece_is_never_safe "$commit_piece"`, so on an ordinary branch:
   - `git -C <dir> commit -m x && git -C <dir> commit --amend -m y` still gets `allow`, because the first commit piece is clean and the amend rides along;
   - `git -C <dir> commit -m x && git -C <dir> reset --hard HEAD~1`, and the same with `git update-ref refs/heads/<b> …` or `git rebase …`, also get `allow`.

   A hook `allow` short-circuits the permission system (`docs/guard-verification.md` row WK30, which the plan cites), so the profile's new `Bash(git commit --amend:*)` deny and its `ask` entries never get a say. That breaks Task 4's own stated goal, *"no harness guard emits `allow` for a `git commit` that rewrites the branch tip"*. It also makes the Context's claim false: the claim says `git update-ref`, `git rebase` and `git reset` are already refused by `dontAsk`, but the commit guard admits them. CS16 (Task 7) is still owed, so the plan itself calls the permission layer *"the measured fast-feedback layer for the incident's own spelling"*. This gap therefore leaves goal 2 resting on an unmeasured layer. (Derived from reading the guard's code. Driving it from this session was refused by the session's own commit guard, so it is not a measured result.)
   **Raised against:** "run `hc_piece_is_never_safe "$commit_piece"`. On `0`, exit `0` with no output."
   **Must hold:** `git-commit-branch-guard.sh` emits no `allow` for any compound in which **any** piece rewrites a commit or moves a branch ref: an amend in any commit piece, not only the first, and a `reset`, `rebase`, `update-ref` or similar piece riding beside a commit. Task 4's decision table covers those compound shapes. The index Context states which ref-moving spellings the permission layer refuses, and does not claim one that a guard `allow` admits.
   **Fix:** In `task_4_plan.md`, apply the refusal to every piece the loop splits, not only to the captured `commit_piece`. One way is to stay silent when any piece fails `hc_piece_is_never_safe`, or when any piece is a git subcommand outside the commit guard's own remit. Add contract rows such as `git -C <dir> commit -m x && git -C <dir> commit --amend -m y` → SILENT and `git -C <dir> commit -m x && git -C <dir> reset --hard HEAD~1` → SILENT. Update the FAIL-CLOSED TABLE, the REPRO block and Task 7's recorded payloads to match. In the story index Context **Permission layer** bullet, correct the `dontAsk already refuses them` sentence to match what Task 4 then guarantees.
