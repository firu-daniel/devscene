## Must Fix

1. **`finding_5.md` and `finding_1.md` leave the mismatch warning's capitalization to two areas** — violates `.claude/context/conventions.md` → `## Shared code, and where it lives` ("A value or behaviour two `cli/src` areas need lives there, never duplicated into both") and `### Where a new responsibility goes` ("A responsibility that already has a home does not get a second one"), and `.claude/context/cli.md` → **One string, one producer.**
   Finding 1 gives `cli/src/machine/pluginCliVersion.ts` the stated rule that one wording serves the refusal, the dry-run note, the upgrade report and `doctor`, and it exports a summary and a remedy that both open in lower case. Finding 5 then has `cli/src/doctor/checks.ts` capitalize the remedy through `sentenceCase`, and has `cli/src/upgrade/report.ts` produce a warning "starting `The installed plugin is version …`" from that lower-case summary. No `sentenceCase` or other capitalizer exists under `cli/src`, and the plan assigns none an owner, so each of the two areas has to write its own and assemble its own sentence. The two warnings can then drift, which is what the new module exists to prevent.
   **Raised against:** "return `` warn(`${pluginCliMismatchSummary(mismatch)}. ${sentenceCase(pluginCliMismatchRemedy(mismatch))}`) ``, or an equivalent that capitalizes only the first letter of the remedy sentence."
   **Must hold:** The complete warning sentence for a plugin and CLI mismatch, capitalization included, has one producer, and neither `cli/src/doctor/checks.ts` nor `cli/src/upgrade/report.ts` assembles or capitalizes it.
   **Fix:** In `finding_1.md`, add an export `pluginCliMismatchWarning(mismatch)` to `cli/src/machine/pluginCliVersion.ts`, returning `The installed plugin is version <plugin> and this CLI is version <cli>. <the remedy with its first letter capitalized>.`, with the capitalization private to that module, and cover its exact text for each `older` value in `cli/test/plugin-cli-version.test.mjs`. In `finding_5.md`, have `PLUGIN_CLI_VERSION_CHECK` return `warn(pluginCliMismatchWarning(mismatch))` and have `upgradeReport` push `pluginCliMismatchWarning(pluginMismatch)`, remove `sentenceCase` and its "or an equivalent" alternative, and align the exact-wording test expectations with that one sentence.

2. **`finding_6.md` allows a second spelling of the `permissions.deny` list key in `report.ts`** — violates `.claude/context/cli.md` → **One string, one producer.** and `.claude/context/conventions.md` → `## Configuration is the source of truth, and it is read at run time` ("a value is imported from its owner rather than retyped").
   The `list` value on each `ProfileEntryDelta` comes from `PROFILE_ENTRY_LISTS` in `cli/src/generators/profileUpgrade.ts`, which builds it as `permissions.${list}` from `PERMISSION_LISTS`, and `ALLOW_LIST_PATH` beside it is the constant `report.ts` already imports to classify by list. Finding 6 makes the deny classification depend on this same value but lets the implementer declare the key "next to the use". A literal in `report.ts` would be a second copy of a key `profileUpgrade.ts` owns, and if the two ever differ the browser-deny group silently stops matching and those entries return to the movable advice.
   **Raised against:** "Add a `permissions.deny` constant next to the use, or export one beside `ALLOW_LIST_PATH`."
   **Must hold:** `report.ts` classifies `permissions.deny` entries through a constant imported from the module that owns the delta's list paths, and declares no list-path literal of its own.
   **Fix:** In `finding_6.md`, replace the either-or with one instruction: export `DENY_LIST_PATH = 'permissions.deny'` beside `ALLOW_LIST_PATH` in `cli/src/generators/profileUpgrade.ts`, and import it in `cli/src/upgrade/report.ts` for both the classification and the sentence.
