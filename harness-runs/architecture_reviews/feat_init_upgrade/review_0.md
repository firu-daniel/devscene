## Must Fix
1. **`task_7_plan.md` gives the run registry's record walk a second home beside `doctor`'s** — violates `.claude/context/conventions.md` → `## Shared code, and where it lives` ("A value or behaviour two `cli/src` areas need lives there, never duplicated into both") and `### Where a new responsibility goes` ("A responsibility that already has a home does not get a second one"), and `.claude/context/cli.md` → `## How a module in this layer is written` ("nothing it reports is re-derived from a second copy").
   `cli/src/doctor/checks.ts` → `liveRunCount` already parses the registry: it reads the file, takes `runs`, skips non-object records and filters on `status`. Task 7 writes a second parser of the same file shape in `cli/src/core/runRegistry.ts`, and Task 11 moves only `pidIsAlive` and `RUNNING_STATUS` across, so both walks remain. The two differ only in what they do with the result (an unreadable file, a record with no pid), and those differences belong to the callers. A later change to the registry's shape would have to be made twice, and missing one would go unreported.
   **Raised against:** "Unparsable JSON or a wrong `{"runs": {…}}` shape is `unreadable`."
   **Must hold:** The registry file's parsing and record walk have one implementation, in `cli/src/core/runRegistry.ts`, and both `readActiveRuns` and `doctor`'s `liveRunCount` consume it, each keeping its own grading.
   **Fix:** In Task 7, export one lower-level reader from `runRegistry.ts` that returns the parsed records or an unreadable state with its detail (a missing file gives no records), and build `readActiveRuns` on it. In Task 11, rewrite `liveRunCount` over that reader, keeping its behaviour: unreadable counts `0`, and only a `running` record with a live pid counts. Add a case to each task's own test for what it changes.

2. **`task_7_plan.md` extends `cli/src/machine/plugins.ts` past what its header states, without amending it** — violates `.claude/context/cli.md` → `## What "done" means here` ("Where the header states a rule, the change either satisfies it or amends the header in the same edit").
   The header opens on "Where this harness's plugin lives", enumerates the files the module reads (`installed_plugins.json`, `known_marketplaces.json` and the `.claude-plugin/marketplace.json` that entry locates), and states "Only the fields a root is navigated for are looked at". `installedPluginVersion` reads a further file, `.claude-plugin/plugin.json`, for a field that navigates to no root. Task 7's Work does not mention this header, although Tasks 1, 3, 4, 6 and 11 each update the header of the module they change.
   **Raised against:** "`plugins.ts`: export `installedPluginVersion(repoRoot?: string): string | undefined`, reading `version` from `<root>/.claude-plugin/plugin.json` at `pluginRuntimeRoot`"
   **Must hold:** After Task 7, the header of `cli/src/machine/plugins.ts` truthfully states every file the module reads and every field it looks at, including the plugin manifest's `version`.
   **Fix:** Add to Task 7's `plugins.ts` Work item: amend the module header to name the plugin manifest under a resolved root as a file it reads, to state that its `version` is the one field read for something other than navigation, and to keep the read-only, navigated-not-validated and every-failure-is-`undefined` statements true of it.

3. **`task_8_plan.md` re-joins the run registry path that `writeProtection.ts` already owns** — violates `.claude/context/conventions.md` → `### Where a new responsibility goes` ("A responsibility that already has a home does not get a second one", and "**Before adding a copy of anything, grep for it.**", whose worked cost is drifted path normalisation).
   `cli/src/generators/writeProtection.ts` → `runRegistryPath` is the existing resolver: `join(repoRoot, normalizeRepoDir(config.stateDir ?? DEFAULTS.stateDir), RUN_LOGS_DIR, RUN_REGISTRY_FILENAME)`. Task 8 spells the join again and states neither the default nor the normalisation. `stateDir` is optional on the config, so a plain join has no value to use where the key is absent. The refusal could then read a different file from the one the profile protects, and a registry that is not there reads as `none`, which permits the upgrade.
   **Raised against:** "Read the registry at `<root>/<stateDir>/${RUN_LOGS_DIR}/${RUN_REGISTRY_FILENAME}`."
   **Must hold:** The path `--upgrade` reads the run registry from comes from the same resolver as the path the write protection covers.
   **Fix:** In Task 3, which already targets `writeProtection.ts`, export `runRegistryPath`. In Task 8, add Task 3 to **Depends on**, call `runRegistryPath(root, config)` and pass the result to `readActiveRuns`. Add a preconditions case with `stateDir` absent from the configuration.

4. **`task_9_plan.md` formats a script invocation that `scriptInvocation` alone may produce** — violates `.claude/context/cli.md` → `## How a module in this layer is written`, **One string, one producer** ("`cli/src/generators/scripts.ts` → `scriptInvocation` is the single producer of `bash <scriptsDir>/<file>`").
   Task 9 has `cli/src/upgrade/report.ts` build this string from its `scriptsDir` input and a `restart-watcher.sh` literal. A hand-built join is wrong for a `scriptsDir` of `.`, the case `scriptInvocation`'s callers rely on it for. No exported constant names this script today: the file name exists only in the `OUTER_LOOP_SCRIPTS` row in `cli/src/generators/outerLoopScripts.ts`, so the literal in `report.ts` would be a second spelling of that row.
   **Raised against:** "Print the restart instruction `bash <scriptsDir>/restart-watcher.sh`"
   **Must hold:** The restart instruction is the output of `scriptInvocation`, given the configured scripts directory and a script name owned by `cli/src/generators/outerLoopScripts.ts`.
   **Fix:** In Task 6, export `RESTART_WATCHER_SCRIPT_NAME` from `outerLoopScripts.ts` and use it in the table row, as `WATCHER_SCRIPT_NAME` is used. In Task 9, build the line with `scriptInvocation(scriptsDir, RESTART_WATCHER_SCRIPT_NAME)`, state that `scriptsDir` is the `outerLoopScriptsDir(config)` value, and add a report case for a `scriptsDir` of `.`.

A mode-only replacement takes no backup, so the plan should state which effect it reports and amend that documentation to match (`.claude/context/cli.md` → `## What "done" means here`, the module-header bullet).
