## Must Fix
1. **`task_5_plan.md` declares a second table of the profile's entry lists beside the one `permissionProfile.ts` already owns** — violates `.claude/context/conventions.md` → `### Where a new responsibility goes` ("A responsibility that already has a home does not get a second one", and "**Before adding a copy of anything, grep for it.**").
   `cli/src/generators/permissionProfile.ts` already declares these lists as `PERMISSION_LISTS` (`allow`, `deny`, `ask`), `SANDBOX_LISTS` (`excludedCommands`, `filesystem.allowWrite`, `filesystem.denyWrite`, `network.allowedDomains`) and `CREDENTIAL_LISTS` (`files` by `path`, `envVars` by `name`), and `assertRunnable` walks them. Nine of the eleven rows Task 5 spells out in `cli/src/generators/profileUpgrade.ts` are those entries, field names included. The plan even cites "the spelling `assertRunnable` uses" while copying it. A list added to the existing tables would then be checked by the render and missed by the `--upgrade` delta and by `doctor`'s drift report, which is the plan's first-named risk ("a profile that loses or gains a grant unnoticed"). Task 5's fixture assertion catches an array missing from one rendered fixture only, so it does not reach a list that fixture does not render.
   **Raised against:** "`PROFILE_ENTRY_LISTS`, one row per list the render can produce, each `{ path, field? }`"
   **Must hold:** Each profile entry list has one declaration. `PROFILE_ENTRY_LISTS` is derived from the declarations `assertRunnable` reads, and spells by hand only the lists those declarations do not cover.
   **Fix:** In Task 4, which already targets `permissionProfile.ts`, export `PERMISSION_LISTS`, `SANDBOX_LISTS` and `CREDENTIAL_LISTS` unchanged, and export `ENABLED_SERVERS_KEY` from the same module. In Task 5, build the `PROFILE_ENTRY_LISTS` rows from those exports (with `SANDBOX_KEY` for the prefix), adding only `permissions.additionalDirectories` and the `ENABLED_SERVERS_KEY` row, and state the two imports in **Depends on**. Keep the labels and the `<path>[].<field>` form the task already specifies. Add the four exports to Task 4's row in the story index's shared-names table.

## Should Fix
- **`task_4_plan.md` leaves one adopter-supplied `allow` shape to reach an `internal()` fault.** The screen covers an entry "naming an `mcp__<server>__` tool" whose server is not started. An entry such as `mcp__foo`, with no tool part, does not match that description, passes Task 2's validation, and then fails `MCP_SERVER_PATTERN` (`/^mcp__(.+?)__/`) inside `assertBrowserWiring`, which throws `internal()` and reports the adopter's entry as a fault in this CLI. `.claude/context/cli.md` → `## How a module in this layer is written` requires the adopter-fixable shape to be screened first with an ordinary `HarnessError`. The screen should refuse every local `allow` entry starting with `MCP_ENTRY_PREFIX` that does not name a server and a tool, and the merge test should cover it. Graded here because it concerns the error contract rather than layering.
- **The story index overstates `runRegistryPath` as "The one resolver of the run registry's path".** `task_11_plan.md` rewrites `liveRunCount` "keeping its behaviour and its path", and that path is the hand join `join(root, stateDir, RUN_LOGS_DIR, RUN_REGISTRY_FILENAME)` in `cli/src/doctor/checks.ts`. Keeping it is defensible: `footprintRow` reads another checkout's configuration tolerantly, through `nonEmptyString`. The table row should say the resolver is the one `--upgrade` and the write protection share, or Task 11 should state why `doctor`'s footprint keeps its own join.
- **`task_5_plan.md`, `task_7_plan.md` and `task_8_plan.md` ask for a header stating the module's rule without the required wording.** `.claude/context/cli.md` → `## Naming and file layout` and `.claude/context/conventions.md` → `## What accompanies a new unit of each kind` fix the words *"The rule this module exists to enforce"*, which Tasks 2, 9 and 10 already quote.
