## Must Fix

1. **`task_3_plan.md` — a `**Verification:**` bullet names test files the unit neither creates nor edits** (`${CLAUDE_PLUGIN_ROOT}/instructions/unit_loop_core.md` → `## The test-run rule`, point 4: *"No `**Verification:**` bullet, finding fix or sub-step names `<test_cmd>`, a gate script, or a test file the unit neither creates nor edits"*, a breach every reviewer raises as a Must Fix.)
   Task 3 writes no test file, yet its last Verification bullet names Task 5's two suites as the evidence for this unit. Those files do not exist when Task 3 ships: Task 5 comes after Task 4, which comes after Task 3. An implementer who reads that bullet as a verification step either runs files outside its own change or reports a check it could not make.
   **Raised against:** "Task 5's suite (`cli/test/planning-driver-walk.test.mjs`, `cli/test/planning-driver-control.test.mjs`) is the behavioural evidence for this library. This task names it as its test task and writes no test file of its own."
   **Must hold:** No Verification bullet in Task 3 names a test file that Task 3 neither creates nor edits. Saying that Task 5 is this library's test task is allowed, but outside the Verification list and without presenting Task 5's files as this unit's evidence.
   **Fix:** Delete that bullet from Task 3's **Verification:**. Add one clause to **What this task does not do.**, which already says *"Task 5 writes its end-to-end suite"*: Task 5 is this library's test task, and this task writes and runs no test file. Do not name the two suite files there.

2. **`task_10_plan.md` — its source guard reads a whole tree, and no task registers it in `treeGuards`** (`${CLAUDE_PLUGIN_ROOT}/instructions/unit_loop_core.md` → `## The test-run rule`, point 8: *"a test that reads a tree of repository files as text … has its `<tree_guards>` entry added to `devscene.config.json` in the same change, or by a later catch-all-layer task the adding task names"*. A missing registration is a Must Fix for every reviewer.)
   The **Source guard.** case of `cli/test/clarification-index-lib.test.mjs` reads every file under `cli/templates/scripts/` as text. That makes it a tree-reading test. No task adds a `treeGuards` entry for it, and Task 10 names no task that will. Without an entry, point 7 never selects this guard for a later unit that adds a third definition under `cli/templates/scripts/`, and that is exactly the drift the guard exists to catch. `devscene.config.json` is root-level and belongs to the `general` layer (`.claude/context/conventions.md` → `## The layers`). So by point 8 the entry belongs to a later `general` task that Task 10 names, not to `cli`-tagged Task 10 itself.
   **Raised against:** "no file under `cli/templates/scripts/` other than `lib/harness-run-lib.sh` defines `hr_max_question_index()` or `hr_top_level_answered_pairs()`."
   **Must hold:** Either the guard reads only fixed, named files and no longer reads the tree, or Task 10 names a later `general`-layer task that adds `{ "test": "test/clarification-index-lib.test.mjs", "covers": "cli/templates/scripts/**/*.sh" }` to `devscene.config.json` → `treeGuards`. In the second case that task lists `devscene.config.json` among its targets and carries the entry as a Work bullet.
   **Fix:** Choose one of the two:
   - (a) Narrow the source guard to the two fixed files it actually needs, `cli/templates/scripts/autonomous-watcher.sh` (defines neither name) and `cli/templates/scripts/lib/harness-run-lib.sh` (defines both). Add nothing to the configuration.
   - (b) Keep the tree read. Add a sentence to Task 10 naming Task 9 as the task that registers the guard. Then add `devscene.config.json` to Task 9's **Targets** and a Work bullet appending that `treeGuards` entry, with a **Depends on:** line naming Task 10.

## Should Fix

1. **`task_6_plan.md` — the driver's start condition adds a third scan of the clarification channel to the watcher.** Step 2 of **The sequence in the launch subshell.** requires *"there is no top-level `question_<n>.md` without its `answer_<n>.md`"*, but does not say which function answers it. The watcher already scans the top level for this in `park_answered_set` (which returns 1 when one is unanswered, but also when no pair is answered) and in `classify_run_exit`'s parked loop. Task 10 exists to give the channel's answers one definition each (`.claude/context/conventions.md` → `### Where a new responsibility goes`: *"Before adding a copy of anything, grep for it."*). Suggested fix: name the function that answers this. Either add `hr_top_level_unanswered` to `lib/harness-run-lib.sh` in Task 10, beside the other two, or derive the answer from an existing helper. Do not plan an inline loop.

2. **`task_3_plan.md` — the prompt-injection screen's `Raised by:` literal is retyped without declaring the driver as a reader.** `pd_entry`'s origin filter matches `Raised by: prompt-injection-reviewer (prompt-injection screen)`. That string is owned by `cli/templates/scripts/prompt-injection-screen.sh` → `PIS_RAISED`, and the script's `READERS OF THESE STRINGS — a rename here is an edit there` block lists every file that keys on it. Today the list holds only plugin files, and `planning-driver-lib.sh` would be its first shell reader outside the script itself (`.claude/context/conventions.md` → *"A literal only one side knows about is a silent contract break"*; *"a value is imported from its owner rather than retyped"*). Suggested fix: add `prompt-injection-screen.sh` to Task 3's targets, with a one-line addition to that READERS block naming `lib/planning-driver-lib.sh` → `pd_entry`. Alternatively, move the constant into `lib/harness-run-lib.sh`, which both scripts already source.

3. **`task_10_plan.md` — the goal claims one definition of the highest-index answer, but a second one remains.** `cli/templates/scripts/prompt-injection-screen.sh`'s park writer picks *"the next index above every question_<n>.md at the top level and under answered/"* through its own `pis_numbered` scan. Task 10 neither moves nor names it, and the source guard checks only function names, so it passes with that scan in place. Suggested fix: either have `pis_park_write` take one above `hr_max_question_index`, adding the screen to Task 10's targets, or narrow Task 10's goal sentence to the watcher and the planning libraries and name the screen's scan as a known remaining copy.

4. **Carried from round 0 (Should Fix 1), now including Task 3: undeclared shell mirrors of plugin contracts.** `prl_*` hard-codes Overrides 3, 4 and 6's path lists and subjects, and the `### 1.3 Templates` ledger line that `prl_ledger_flip` rewrites. That means revisiting register row 11's `no-change`.
