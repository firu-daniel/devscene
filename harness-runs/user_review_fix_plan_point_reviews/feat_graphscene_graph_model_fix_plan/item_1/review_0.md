# graphscene review — 1. `_ecma_pattern` translates only `$` and `.` and silently passes every other construct, so a later schema `pattern` can make `load_graph` and gate 3g's `ajv` disagree again — iteration 0

## Should Fix
1. **A quantifier directly after a quantifier passes the translator, so Python 3.11+'s possessive `*+` / `++` / `?+` / `{n}+` is accepted** — `graphscene/src/graphscene/loader.py` (`_ecma_pattern`) — "Any other construct raises `ValueError` naming the pattern's schema path"
   `_ecma_pattern` looks at each `*`, `+`, `?` and well-formed `{n,m}` on its own and never checks what comes before it, so `^a*+$`, `^a++b$`, `^a?+$` and `^a{2}+$` all pass through unchanged. The package needs Python `>=3.11`, and since 3.11 `re` reads these as possessive quantifiers. ECMA-262 under the `u` flag rejects every one of them. So the docstring's claim that any other construct raises `ValueError` is false. A schema `pattern` like that would build `_validator` and load graphs in Python, while gate 3g's `ajv` refuses to compile the schema at all. The divergence is loud on the `ajv` side, not silent, so this does not reach Must Fix. But it is exactly the case the guard exists for: the schema change should force a decision about the translator, and here it does not.
   Confirmed: the ECMA side was run as a probe. `bash scripts/scratch-run.sh harness-runs/scratch/possessive_probe.mjs` printed `Invalid regular expression: /^a*+$/u: Nothing to repeat`, and the same for `^a++b$`, `^a?+$`, `^a{2}+$` and `^(?:ab)*+$`. The Python side was confirmed by **reading only**: the interpreter on PATH is 3.9, which has no possessive quantifiers and cannot import `graphscene` (`TypeAlias`). What I read: the `_ecma_pattern` branches (`*`, `+` and `?` fall through to "out.append(char)", and the `{` branch appends `quantifier.group()` with no check on what came before), plus the Python 3.11 `re` documentation on possessive quantifiers.
   **Fix:** In `_ecma_pattern`, track whether the previous emitted token was a quantifier. That is a `*`, `+`, `?` or `_QUANTIFIER` match, with one exception: a single `?` straight after a quantifier marks it lazy and is valid in both engines. Refuse any further `*`, `+`, `{…}`, or a second `?`, naming that character. For example `refuse("+")` for `^a*+$`. Add `("^a*+$", "+")` and `("^a{2}+$", "+")` to `test_an_untranslatable_pattern_construct_is_refused`. Add a lazy case such as `"^a+?b$"` to `test_supported_constructs_translate_unchanged_but_for_dollar_and_dot`.
