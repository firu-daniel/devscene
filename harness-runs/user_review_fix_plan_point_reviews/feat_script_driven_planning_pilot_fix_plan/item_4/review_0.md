## Must Fix
1. **The library header still says every commit the driver makes is one the autonomous fork defines, and the new escalation-park commit is not** — `cli/templates/scripts/lib/planning-driver-lib.sh` (module header) — "Where the walk enters, and what each printed line commits, are the autonomous planning fork's"
   The header says what each walker line commits comes from `task_plan_writing_instructions_autonomous.md` → Override 2, 5 and 6. That fork defines a `Plan round <n> partial` commit only for a PAUSE (Override 5) and for the API-overload self-pause. Override 6 commits a round only when the walker prints a `round:` line. Nowhere does it commit a held round at an `<escalate>`. The new block in `pd_escalate_park` ("if [ \"$held\" = yes ]; then pd_partial …") adds a commit the fork does not have. This also means the orchestrated path still leaves a held round uncommitted, so the two drivers now behave differently on a path (b) resume. A maintainer who trusts the header will wrongly conclude the two drivers commit the same set, and so resume the same way. That includes the `general`-layer dispatch that will write `docs/flow-graph-walker.md` → `### A resume after an escalation park` from this unit's notes. `.claude/context/cli.md` → `## What "done" means here` says a change must satisfy its module header or amend it in the same edit.
   **Fix:** Amend the header in this edit. State that the driver adds one commit the fork does not define: at an `<escalate>` carrying `held:` lines, the `chore: Plan round <n> partial for <branch>` commit of Override 6's path set, made before the park, so that a resume reads the passed gates' evidence as committed. Say that the orchestrated path does not make this commit. Add the same divergence to `finding_4.md`'s **Deviations from plan:**, so the `general`-layer docs block records that path (b) re-dispatches only the escalated gate on the script-driven path only.

## Nice to Have
1. **The stub header leaves out the side effect of a `findings` value that differs from a PASS/FAIL outcome** — `cli/test/helpers/planning-driver.mjs` (header) — "`findings`, on a gate, is the verdict (`PASS` or `FAIL`) of the findings file it writes whatever its outcome"
   When `outcome` is `PASS` or `FAIL` and `findings` names the other verdict, the stub writes the file but omits `findings_file` from the decision (`if (verdict === decision.outcome)`). `pd_reap_one` then records that as an `error` ("`FAIL` or `PASS` without `findings_file`"). The header does not say so. A later case author who combines the two would get an unexplained `error`.
   **Fix:** Add a clause to the header: "with `outcome` `PASS` or `FAIL` and a different `findings`, the decision carries no `findings_file`, which the driver records as `error`."
