## Decided (2026-11-22)

- **The harness side lives in `devscene-flow-host/`,** the harness's GraphScene host package, which #451 created and #455 renamed, and which stays in this repository for good (#425). It depends on `graphscene`, and GraphScene never imports it.
- **What goes where.** Anything useful without DevScene goes into GraphScene. `devscene-flow-host` holds only DevScene's meanings: what it reads from `devscene.config.json`, the run mode and the ledger, the `stateDir` paths, the plugin's reviewer files and documents, and the `flow-walker.sh` wire format. LangGraph splits things the same way: generic stores and patterns ship as packages (`langgraph-checkpoint-*`, prebuilt agents), and an application's glue stays application code.
- **It grows past this branch.** The round and reviewer files (#464) and the `flow-walker.sh` compatibility command (#465) come next. It also gets the harness's `claude` executor configuration (#421), the planning graph's hooks and prompt sources (#423), and the planning driver's entry (#424).
- **Adopters never import it.** It ships inside the `devscene` npm package with `graphscene` (#419), and an adopter reaches it only through the scripts `init` writes. A project without DevScene uses GraphScene alone (#425). _Refined 2026-11-23 in #419 → Decided: a full cutover, so `flow-walker.sh` runs this package's compatibility command for every caller, and DevScene requires `uv`._
- **Resuming a round from its files uses #450's generic entry.** Moved to #464 on 2026-11-23.

- **This branch sets `devscene-flow-host`'s internal structure.** #451 ships the package with its boundary test only and no internal layers. Planning decides what goes in and the layers it goes into together, and the code lands in them from the start: the layer folders, an `import-linter` layers contract in `pyproject.toml` as `graphscene` has (#434), and the `README.md` updated. The structure has to leave room for what comes next (#464, #465, #421, #423, #424), not only for this branch.

- **A starting shape for the layers** (the planning session decides it). The list above sorts into roughly three parts: reading the repository's records (`devscene.config.json`, the ledger, round files, reviewer files) into values; the host that answers GraphScene's protocols over those values (`PredicateHost`, the store, the reviewer-file rules, the resume over #450); and the `flow-walker.sh` compatibility command (argument parsing, rendering a `Step`, exit codes). Imports would point from the command, through the host, to the readers, with only the host and the command importing `graphscene`. `graphscene`'s own split (`model` / `adapters` / `engine` / `facade`, `.claude/context/graphscene.md` → `## The internal layers`) is the in-repo precedent, not a template: this package is glue, and fewer layers may be enough. _Split 2026-11-23:_ the three parts now land across three branches: the readers and the host here, the round and reviewer files in #464, and the command in #465. The structure this branch sets has to hold all three.
- _Moved to #465 on 2026-11-23: GraphScene's own CLI is #452's (shipped by #460), and the compatibility command is built over the library rather than over that CLI._
- **The walk's branch is not in GraphScene's state** _Raised 2026-11-23._ `WalkState` records the `flow` but no branch (`graphscene/src/graphscene/model/walk_state.py`). `flow-walker.sh` refuses a state file written for another branch (exit 1, *"a flow or branch other than the state's"*), and that matters in the main checkout, where terminal runs on different branches share one `<stateDir>`. Without that check, `current` could hand a branch another branch's walk. The host records and checks the branch beside the walk, or keys the store by branch; which one is this branch's.
