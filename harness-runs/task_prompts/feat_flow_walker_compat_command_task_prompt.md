`feat_flow_walker_compat_command` adds `devscene-flow-host`'s `flow-walker.sh` compatibility command: `flow-walker.sh`'s verbs, flags, output and exit codes, built over the host from #418 and the round-file rules from #464. Part of #376.

_Split out of #418 on 2026-11-23, so that each of #418's three parts is planned on its own: #418 keeps the host, #464 takes the round and reviewer files, and this branch takes the compatibility command._

## Why

#419 switches `flow-walker.sh` to the Python walker for every caller, with no bash fallback, by handing off to this command. Callers and their suites must see the same output they parse today.

## Decided (2026-11-24)

- **Where the host's way is better than bash's, the host's way wins.** The command keeps `flow-walker.sh`'s wire grammar wherever a caller parses it: the `key: value` keys and their order, the exit codes and the actions. A change there lands with the change to every caller that parses it. How the walk routes may follow the host where the host has a better rule. Each such difference is listed on the branch (in the package README), so that #419 updates the `flow-walker*` suites that pin bash's behaviour instead of rediscovering it. This replaces "byte for byte" as the bar.
- **This branch closes #464's non-round findings-file gap.** #464 (#471) requires a findings file on a non-round reviewer's `FAIL` (`ui_review`) but does not keep it, and drops one given with `answered`. So `ui_writer`'s revision reaches the writer with no `arg.findings_file` (`devscene-flow-host/src/devscene_flow_host/host/round_gates.py` → the `TODO: @claude` in `record_outcome`'s non-gate branch; `devscene-flow-host/README.md` → **Recording a gate.**). Bash keeps it as `revision_findings` and clears it on `start` (`flow-walker.sh` → `next`, the `<ask>` branch). The flow needs that line: `ui-tests-plan-writer`'s revision prompt reads it, and `cli/test/flow-walker-ui-and-reentry.test.mjs` pins it. The gap closes with a host-side record of that file, and its `TODO: @claude` marker is removed. Where the record lives is the planning session's call; #464's refusal record beside the walk is the precedent.
- **The other `TODO: @claude` marker in `host/round_gates.py`, the held-gate escalation, is not this branch's.** It is #472, ordered after this branch and before #419.

## Leads

_The leads below are starting points from #376, #418 and the discussion that split it, not requirements. The planning session decides what holds when this branch is planned._

- **A command line with `start` / `next` / `current` / `check-round-file` and `flow-walker.sh`'s flags** (moved from #418), so existing callers and suites can switch over unchanged.
- **Rendering a GraphScene `Step` as `flow-walker.sh`'s `key: value` output, exit codes 0–3 and its one-line stderr message** (moved from #418). Callers parse the output in `planning-driver-lib.sh`, `planning-node-lib.sh` and `plugin/instructions/task_plan_writing_instructions_core.md`, plus `user_review_fix_plan_writing_instructions_core.md`, which #419 lists. Those parsed lines keep bash's form (see **Decided** above). A refusal's stderr text may be the host's own wherever no caller parses it. The grammar is in `flow-walker.sh`'s header: the `skip:`, `round:`, `ledger:`, `report:` and `refused:` lines, and `current` re-printing the pending action unchanged.
- **Mapping `flow-walker.sh`'s review-loop arguments onto the engine** _From #417 as merged (#448, 2026-11-22), moved from #418._ #417 kept these rules out of the engine and left them to this entry. `--findings <path>` becomes `detail` in `Walker.next(outcome, node, detail)`, which lands in `GateRecord.detail`. `arg.iteration` is the `Dispatch`'s `round_number`. `arg.review_mode` (`full` / `converging`) is `Dispatch.converging`, which is `None` on a plain round. A revision's `arg.findings_file` lines are the `closed_round` records' `detail`s, in `gates` order. _Updated after #464 (#471, 2026-11-23)._ #464 did this mapping: `host/round_gates.py` → `record_outcome` takes the findings file and applies the reviewer-file rules before it calls `Walker.next`. So the command records an outcome through `record_outcome`, starts through `host/re_entry.py` → `start_walk` and re-reads through `current_step`, never through `Walker` directly. Calling `Walker` directly would skip the round-file check, the refusal count and the `refused:` lines.
- **Concurrency:** `start` and `next` hold a lock from before the state is read until after it is replaced, so several calls can record a set's gates at once and exactly one of them prints the round's result. A call that gives up waiting exits `2` (`flow-walker.sh` → `CONCURRENCY`; `cli/test/flow-walker-concurrency.test.mjs`). _Updated after #464 (#471)._ The host now takes two locks: `RefusalStore`'s lock (`<stateDir>/.flow_walker_state/round_refusals/<branch file>.lock`) first, then the walk store's own. `record_outcome` and `start_walk` hold both, and `current_step` takes neither. Each lock times out after 120 s with a `TimeoutError`, so a call can wait about 240 s where bash gives up after 120 s. Both timeouts map to exit `2`. Whether to share one budget across the two locks is the planning session's call.
- **Launching without reaching the network** (`uv run --frozen --no-sync`), with the entry declared in `[project.scripts]` as #452 did for `graphscene`. A console script is installed only by `bash scripts/python-service.sh provision`, so a test drives the module directly.
- **It is built over the library, not over GraphScene's CLI** (moved from #418). GraphScene's own CLI (#452, shipped by #460) stays generic, and its JSON is not this wire format.
- **Evidence of agreement:** the six `cli/test/flow-walker*.test.mjs` suites pin the bash walker's output, and running them against this command is #419's. This branch may still compare the two walkers on the same fixtures, so that #419 starts from a list of known differences: those the host chose deliberately (see **Decided** above), and those still open.
- **"No walk in progress" stays an exit-1 refusal with bash's message** _Raised 2026-11-23._ `next` and `current` with no saved walk refuse with `no walk in progress at <state file>: run 'start' first` (`flow-walker.sh`, exit 1). The orchestrator reads `current`'s exit 1 as the answer *"no saved walk"* and its exit 2 as a blocker (`plugin/instructions/task_plan_writing_instructions_core.md` → the paragraph after **Continuing a saved walk.**). A Python `StateStore.read()` that returns `None` must map to that exit 1, never to exit 2.

- **What #418 left for this command** _From #418 as merged (#467, 2026-11-23)._ The command lands in the `commands` layer (`.claude/context/devscene-flow-host.md` → `## The internal layers`). That layer owns locating and loading the graph file, rendering a `Step` or a refusal, and the exit status a `RecordError` or an unexpected exception becomes (`## Not determined` there). `--skipped` maps onto `host/walking.py` → `open_walker(repo_root, branch, graph, skipped=…)`. A predicate the host cannot answer gives its reason through `HarnessPredicateHost.refusal_reason` (`host/predicates.py`).
- **Three wire differences #418 created** _From #418 as merged (#467, 2026-11-23)._
  - The run-mode refusal text differs from bash's. `records/ledger.py` → `read_run_mode` says `no run-mode record: no flow-progress ledger for '<branch>' and no skipped ids given`. `flow-walker.sh` says `… and no --skipped`. Either the command renders bash's text, or the reader's text changes.
  - The state file is now per branch, at `<stateDir>/.flow_walker_state/<quote(branch, safe="")>.json` (`host/store.py`). So `no walk in progress at <state file>` names that file, not bash's flat `<stateDir>/.flow_walker_state`.
  - Bash's refusal of a state written for *another branch* ("a flow or branch other than the state's", exit 1) can no longer happen: another branch's walk is never read. Only a mismatched flow still refuses.
- **The lock's timeout.** `host/store.py` → `walk_store` gives `FileStateStore` `lock_timeout=120.0` by default, and the lock file is `<branch file>.lock` inside the state directory. Compare that with bash's `CONCURRENCY` wait before a call that gives up maps to exit `2`.
- **What #464 left for this command** _From #464 as merged (#471, 2026-11-23)._ The host's public names are listed in `devscene-flow-host/README.md` → `## The layers`.
  - `check-round-file`: `records/round_files.py` → `round_file_problem` gives the reason a round file is refused, or `None`. Its exit `3` and its output are this command's, as is the `refused:` line rendered from `HostStep`'s refusals (`host/round_gates.py`).
  - A non-round reviewer's `arg.iteration` comes from `host/reviewers.py` → `review_iteration`.
  - The round-cap payload (`rounds:` / `evidence` lines) comes from `records/index_evidence.py` → `read_index_evidence` and `records/round_evidence.py` → `read_round_evidence`.
  - Errors the command must map to an exit status (`devscene-flow-host/README.md` → `## Errors`): a malformed refusal record raises `ValueError`, its lock raises `TimeoutError`, and a round gate with no `findingsFolder` raises `ValueError`.
  - The held-gate departure, while #472 is open: with a held gate and only refused gates out, the host re-dispatches the refused gates and escalates at that round's next join, where bash escalates at once (`flow-walker.sh` → `ROUNDS`, *"With none out: a held gate escalates"*). It is a known difference for the comparison above.
