### Task 1 — Give `qa-tester` a schema-validated return with a non-halting `blocked` outcome and move Phase E, Phase QA and the supervised QA flow onto it

**Goal:** `qa-tester` replaces its four fenced return lines — `verdict: PASS`, the three-line `verdict: FAIL` block, `error: blocked — test <T>: <cause>` and the unmarked `error: <reason>` — with one fenced `json` return object declared in `plugin/schemas/qa-tester.return.json`. Every caller moves onto that object in the same change: the plan-orchestration core's Phase E, the user-review-fix flow's Phase QA (core and autonomous fork), and the supervised QA flow. The distinction callers act on is kept: a blocked test is never a pass and the phase continues past it; a run that cannot proceed halts.

**The contract this task defines** (every outcome one token, `harness-runs/lessons.md` → `## Agent prose`):

- An `outcome` of `PASS` — every assertion held and no part of the test was blocked. No other field.
- An `outcome` of `FAIL` — the test produced at least one finding, of any severity. Both required:
  - `findings_file` (string, non-empty): the full path of the index written — `qa_review_<iteration>_t<T>.md` in per-single-test mode, `qa_review_<iteration>.md` in the full-run mode.
  - `must_fix_count` (integer, at least 0): a Should Fix alone makes a valid `FAIL` with `0`.
- An `outcome` of `blocked` — no finding, and a part of the run was blocked for a reason confined to that test. Required:
  - `blocked_tests` (array of objects, at least 1 item). Each item, both properties required:
    - `test_id` (integer, at least 1): the blocked test's number.
    - `cause` (string, non-empty): one line naming why it could not be driven.

  Per-single-test mode returns one item; the full-run mode one item per blocked test. This is the former `error: blocked — ` return. Per `docs/structured-agent-returns.md` → *An agent's own `error:` return becomes an outcome, never `error`*, a non-halting return becomes *"an outcome of its own, named for the result it reports and never `error` or `blocker`"*, and *"The literal a caller matched before becomes the outcome value it routes on"* — `blocked`.
- An `outcome` of `blocker` — nothing in the run can proceed. Required:
  - `blocker` (string, non-empty): the one-line reason — e.g. `application not reachable at <base_url>`, or the driver-gate sentence naming the configured driver.

  This is the former unmarked `error:` return, which every caller halts on.

Task 2 gives the two mobile stubs a schema that is the `blocker` variant above alone, with the same field name; this task changes neither stub.

**How every caller routes the return.** State it at each dispatch site, reading as `${CLAUDE_PLUGIN_ROOT}/instructions/agent_return_contract.md` → `## Reading a return` states:

- An `outcome` of `PASS` → the existing pass arm (mark-pass in Phase E and Phase QA; collect in the supervised flow).
- An `outcome` of `FAIL` → the existing fail arm, `` `qa-tester.findings_file` `` and `` `qa-tester.must_fix_count` `` taking the place of the old path and count lines.
- An `outcome` of `blocked` → the existing per-test blocked arm: record each `` `qa-tester.blocked_tests.test_id` `` with its `` `qa-tester.blocked_tests.cause` ``, leave the test `[ ]`, and continue. It is never a pass and never a stop.
- An `outcome` of `blocker`, **or** the third consecutive return that fails the check → the existing halt arm, reporting `` `qa-tester.blocker` `` or the check that failed. **This is the site's `error` route**; name it so at each site.
