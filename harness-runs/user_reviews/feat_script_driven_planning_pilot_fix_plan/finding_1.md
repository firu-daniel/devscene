### 1. Replace the watcher tunable `PLANNING_DRIVER_PLUGIN_DIR` with a `devscene.config.json` key so remote jobs take script-driven planning too

**File:** `cli/templates/scripts/autonomous-watcher.sh` (`planning_driver_ready`) — "job mode always takes the orchestrated path"

**Problem.** The pilot's switch is the watcher tunable `PLANNING_DRIVER_PLUGIN_DIR`, a machine-local absolute path (header block `SCRIPT-DRIVEN PLANNING IS AN OPT-IN PILOT.` → "THE SWITCH is the tunable PLANNING_DRIVER_PLUGIN_DIR … a watcher setting rather than a devscene.config.json key because its value is a machine-local path"). That choice shuts out remote runs:

- `planning_driver_ready` returns 1 with `PLANNING_DRIVER_OFF_REASON="job mode always takes the orchestrated path"` whenever `JOB_MODE` is `1`.
- No `env:` block in `cli/templates/github/workflows/devscene-run.yml` maps the tunable, so a job never sees it anyway.

The pilot saves the orchestrator's cache-read tokens. A remote run pays those tokens the same way a local one does, so the user wants remote runs to take the saving as well. A committed path cannot be right both on the operator's machine and on a runner. So the switch becomes a boolean and the plugin directory is derived at run time.

**Fix.**

1. **A new configuration key, as one contract in four places** (`.claude/context/conventions.md` → `### The order files are created…`, item 1; `## What accompanies a new unit of each kind`, row *A configuration key*). Use a boolean, default `false`. The suggested home is `execution.scriptDrivenPlanning`, beside `execution.keepAwake`, because `execution` already holds the switches the run watcher reads. Add it in this order:
   - `schemas/devscene.config.schema.json` → `properties.execution.properties`, with a description stating that it is off by default, read by the run watcher in both local and job mode, and applies to the task engine's planning only.
   - `cli/src/config/model.ts`: the `ExecutionConfig` field with the description condensed to one line, the `DEFAULTS.execution` entry `false`, and a one-function reader beside `keepAwakeEnabled`.
   - `cli/src/config/check.ts`: add it to `EXECUTION_KEYS`, add a `checkBoolean(execution, 'scriptDrivenPlanning', 'execution', problems)` call, and extend the doc comment that lists the declared boolean keys.
   - `docs/config.md` §5: its row. Also extend the `## 2. Where configuration lives` paragraph that explains why `execution.progressComments` and `execution.keepAwake` are committed keys.
2. **The shell reader.** In `cli/templates/scripts/lib/harness-run-lib.sh`, add one reader shaped like `hr_keep_awake`, for example `hr_script_driven_planning <root>`. It prints nothing and answers through its status: 0 for `true`, 1 for `false` or absent, 2 when the configuration is unresolvable or the value is not a boolean. Declare it as the shell mirror of the model's reader. Like `hr_keep_awake`, the watcher passes it the **main** checkout (`$MAIN_REPO`), never a run copy, whose `devscene.config.json` a session can rewrite. In a job, the main checkout is the job's own checkout.
3. **Derive the plugin directory; never configure it.** The directory every node session pins with `--plugin-dir`, and adds with `--add-dir`, is the plugin's **runtime root**: the directory the run already loads the plugin from in that execution mode.
   - **Locally:** the operator's installed copy.
   - **In a job:** the copy the `Install the pinned plugin` step installs from the tag clone at `$RUNNER_TEMP/harness-marketplace`. That is a `directory`-sourced marketplace, so the runtime root is `<installLocation>/plugin`.

   `cli/src/machine/plugins.ts` → `pluginRuntimeRoot` already answers this question from the runner's records: `installed_plugins.json` and `known_marketplaces.json` under the Claude home, with `CLAUDE_CONFIG_DIR` honoured as `run-analytics.sh` mirrors it. Add a read-only shell mirror of it to `harness-run-lib.sh`, for example `hr_plugin_runtime_root_var`, re-derived at every launch and never cached. Declare that mirror in the header of `cli/src/machine/plugins.ts`, which states that the roots are resolved there and nowhere else in the CLI, and amend that header sentence in the same edit (`.claude/context/cli.md` → *A reviewer holds a change to its module's own header*). Before writing the mirror, grep `cli/templates/scripts/` for an existing resolver of the installed plugin's path, and reuse it if one exists.
4. **The watcher.**
   - Delete the `PLANNING_DRIVER_PLUGIN_DIR` tunable outright: its default line (`PLANNING_DRIVER_PLUGIN_DIR="${PLANNING_DRIVER_PLUGIN_DIR:-}"`), its slot on the `tunables:` status line, and every header and comment mention. Ship no fallback that still reads it, and no sentence saying it was renamed. Per the lessons ledger, a breaking rename ships no compatibility path.
   - In `spawn_engine`, gate the pilot on the new key instead of `[ -n "$PLANNING_DRIVER_PLUGIN_DIR" ]`.
   - In `planning_driver_ready`, remove the `JOB_MODE` refusal. Resolve the runtime root, and give a not-ready reason when none resolves (for example `the plugin's runtime root could not be resolved from the agent runner's records`). Keep every other readiness check (task engine, the three libraries, `plugin.json` and the planning core readable under the derived root, ledger pending), now against the derived directory.
   - Hold the derived directory in one variable set at readiness, for example `PLANNING_DRIVER_PLUGIN_ROOT`. Use it everywhere the old tunable was read: the `--add-dir` / placeholder-manifest roots (`${planning_driver:+"$PLANNING_DRIVER_PLUGIN_DIR"}`, twice), `PD_PLUGIN_DIR=` in `planning_driver_run`, and its `driving its planning with …` log line.
   - Rewrite the header block `SCRIPT-DRIVEN PLANNING IS AN OPT-IN PILOT.` (THE SWITCH, IT PINS THE PLUGIN, LOCAL MODE ONLY, READY) to match, and drop the LOCAL MODE ONLY bullet. Also update the REPRO comment near line 1139, which sets `PLANNING_DRIVER_PLUGIN_DIR=` on the command line.
5. **A remote job runs the same three steps as a local run.** With the key on, a job launch runs the setup session, then `pd_drive`, then the engine session. Check each of the following on the job path and change what does not hold:
   - The job profile's plugin-root grant (`init --plugin-root-entries`) covers the derived directory, so a node session can read the agent files there.
   - `--add-dir` of that directory is accepted by the job's sandbox. The job's own `extra_dirs` dedupe should keep the directory from being passed twice.
   - The `.planning/` stream directory beside the run log is created under the job's log directory.
   - The dispatch counter and walker state cross a job boundary in the bundle as they already do (`docs/remote-execution.md` → **The walker state.**).
   - The watcher's `job_qa_remote_skipped` clause still reaches the setup session's prompt.

   - `docs/flow-graph-walker.md` → `## 5. The two drivers` → `### Which runs when`: **Decision.** and **Reason.**, which today argue for a watcher tunable over a config key. Also update `### The schema-from-graph rule, and the init check` (`--plugin-dir <switch>`), `### Why the prompts come from the pinned plugin's core` (`<switch>/instructions/…`), and the hand step in `### Not yet measured, and the hand step that measures it`. That hand step sets the switch through `watcher.env`; it now turns the key on. Keep every adopter command in its own fenced block, one command per line. The third unmeasured fact, whether an installed copy shadows `--plugin-dir`, should say that the pinned directory is now the installed copy's own runtime root.
   - `docs/remote-execution.md`: state that a job takes script-driven planning when the key is on, and where its plugin directory comes from (the pinned plugin the job installs). A short paragraph in `## 3. A remote run supervises itself`, or wherever that document lists what a job runs, is enough. Also check its §6 *What is not verified here* table for a row the remote launch now needs.
   - Grep `docs/`, `cli/README.md`, `cli/templates/scripts/README.md`, `ARCHITECTURE.md` and `plugin/` for `PLANNING_DRIVER_PLUGIN_DIR`, and update every hit.
